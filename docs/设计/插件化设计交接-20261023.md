### 1.4 诊断结论（一句话）

> **问题不在补丁质量，而在补丁是唯一扩展机制，且扩展点是可变的文本。**
> 补丁已经做到了它能做到的极限：唯一命中断言、失败整份不写盘、MARKER 防重。
> 剩下的风险全部来自一个事实——**扩展点没有类型、没有签名、没有版本、没有归属。**

## 2. 设计目标与非目标

### 2.1 目标

| # | 目标 | 可判定标准 |
| --- | --- | --- |
| G1 | 新增一个功能**不需要改 `src/bridge.js`** | 新增插件后 `bridge.js` 字节数不变（`stat -c%s` 前后相等） |
| G2 | 两个插件**改同一个扩展点不会冲突** | `prompt.build` 改为返回行对象；两个插件各自返回 `{mood}` / `{affinity}`，由注册表合并 |
| G3 | 单个插件崩溃**不拖垮整条链** | 一个 handler 抛异常 → 记 panic、保留上一个值、后续 handler 继续跑 |
| G4 | 插件可**独立启停**（配置层面） | `plugin.json` 的 `enabled=false` 或 `cfg.socialV2.tools.<flag>=false` → 该插件的 hook 不注册 |
| G5 | 全程**零新增依赖、零构建步骤** | `package.json` 的 `dependencies` 不变；没有 tsc/babel/rollup；`node src/bridge.js` 仍能直接跑 |
| G6 | 迁移可**分步发布**，每步都能回滚 | 见 §7，每步都有「不满足就 `git checkout` 那一个文件」的退回路径 |

### 2.2 非目标（写清楚，避免 Codex 跑偏）

- **不做独立进程 / 独立服务 / 子进程**。理由：MemAvailable 只剩 **507 MB**，swap 已用 **1152 MB**。现在整个桥接只吃 **76.2 MiB**（`MemoryCurrent=79884288`）。任何「每个功能一个常驻进程」的方案在这里都是自杀。
- **不做 RPC / 消息队列 / IPC**。理由同上，且这些都要序列化边界，等于把「函数调用」换成「网络调用」，延迟和故障面都变大。
- **不改 `cfg.socialV2.tools.<flag>` 的语义**。工具开关仍是这套键，插件只是「知道自己拥有哪些 flag」。
- **不动人格/仿真提示词的分层**（`dsh/agent-presets/qq-chat-v2/agent.cordis.yml` 的 `persona.prefix` 与 `roles/<角色>.md`）。插件化只改「桥接怎么拼 prompt」，不改「prompt 里写什么」。
- **不追求一次性把 14530 行拆成 50 个文件**。只搬「功能层」，`main()` 里的核心状态机（会话/队列/发送/DSH 连接）留在原处。

## 3. 核心机制：钩子注册表

### 3.1 设计要点

1. **同进程、纯函数、无依赖**。`src/hook-registry.js` 只依赖语言本身（ESM，与仓库现有 `src/*.js` 一致——`bridge.js` 用的是 `} from './group-digest-store.js';` 这种 ESM 多行 import）。
2. **`use(name, plugin, fn, order)` 注册；`runChain` 串行改值；`runAll` 广播**。两种语义分开，不要混：`prompt.build` 要「改值」，`wake.tick` 只要「通知」。
3. **`order` 决定顺序，`seq` 决定同 order 的先后**。稳定排序（`a.order - b.order || a.seq - b.seq`），这样同一批插件在多次启动间顺序一致——**顺序可复现**比顺序「正确」更重要，否则行为无法复现就无法排障。
4. **单个 handler 抛异常 → 记 panic，保留上一个返回值，继续跑下一个**。这是「2G 机器上一条 prompt 拼装链不能因为一个插件的 `undefined` 而整条失败」的硬要求。参照 `src/bridge.js:3655-3659` 记录的那次事故：一个 `ReferenceError` 就让整条唤醒失败。
5. **`panics` 有界（最近 50 条）**。内存只有 507 MB，不能让它无限长。
6. **`describe()` 供 `/api/_plugins` 读**。这是 Step 0 的验收钩子（见 §7）。

### 3.2 参考实现 `src/hook-registry.js`

```js
// src/hook-registry.js —— 同进程钩子注册表。无依赖、无构建步骤、约 50 行。
// 设计约束：2G 机器上不许多进程；prompt 拼装链不能因为一个插件抛错就整条失败。

export class HookRegistry {
  constructor({ onPanic, maxPanics = 50 } = {}) {
    this.hooks = new Map();            // name -> [{ plugin, fn, order, seq }]
    this.seq = 0;
    this.maxPanics = maxPanics;
    this.panics = [];                  // 最近的 panic，供 /api/_plugins 暴露
    this.onPanic = onPanic || ((info) => {
      // 走桥接既有的 log()，落 /var/log/qqbridge.log
      console.error(`[hook] panic ${info.hook} <- ${info.plugin}: ${info.error?.message ?? info.error}`);
    });
  }

  /** 注册。order 越小越先跑；同 order 按注册先后。返回注销函数。 */
  use(name, plugin, fn, order = 100) {
    if (typeof fn !== 'function') throw new TypeError(`hook ${name}: handler 必须是函数`);
    const list = this.hooks.get(name) ?? [];
    list.push({ plugin, fn, order, seq: this.seq++ });
    list.sort((a, b) => a.order - b.order || a.seq - b.seq);
    this.hooks.set(name, list);
    return () => this.unuse(name, plugin);
  }

  unuse(name, plugin) {
    const list = this.hooks.get(name);
    if (!list) return;
    this.hooks.set(name, list.filter((h) => h.plugin !== plugin));
  }

  /** 串行改值语义：上一个的返回值喂给下一个。返回 undefined = 不改。单点异常不外溢。 */
  async runChain(name, value, ctx) {
    let current = value;
    const failed = [];
    for (const h of this.hooks.get(name) ?? []) {
      try {
        const next = await h.fn(current, ctx);
        if (next !== undefined) current = next;
      } catch (error) {
        failed.push({ plugin: h.plugin, message: error?.message ?? String(error) });
        this.onPanic({ hook: name, plugin: h.plugin, error });
      }
    }
    if (failed.length) this.#remember({ at: Date.now(), hook: name, failed });
    return { value: current, failed };
  }

  /** 广播语义：不关心返回值，异常一律吞掉并记 panic（用于 wake.tick / turn.lifecycle）。 */
  async runAll(name, payload, ctx) {
    for (const h of this.hooks.get(name) ?? []) {
      try {
        await h.fn(payload, ctx);
      } catch (error) {
        this.#remember({ at: Date.now(), hook: name, failed: [{ plugin: h.plugin }] });
        this.onPanic({ hook: name, plugin: h.plugin, error });
      }
    }
  }

  #remember(row) {
    this.panics.unshift(row);
    if (this.panics.length > this.maxPanics) this.panics.length = this.maxPanics;
  }

  /** 给 /api/_plugins 的自描述。 */
  describe() {
    const out = {};
    for (const [name, list] of this.hooks) {
      out[name] = list.map((h) => ({ plugin: h.plugin, order: h.order }));
    }
    return { hooks: out, panics: this.panics };
  }
}
```

用法（在 `main()` 里，`src/bridge.js:1488` 之后、任何 hook 被调用之前）：

```js
const hooks = new HookRegistry({ onPanic: (i) => log(`[hook] panic ${i.hook} <- ${i.plugin}: ${i.error?.message}`) });
const ctx = { hooks, cfg, log, S, /* …见 §4.6 的注入清单 */ };
await loadPlugins(ctx);   // src/plugin-loader.js
```

### 3.3 为什么不引入 `@marcopeg/hooks` / `@forrestjs/core`

| 候选 | 结论 | 理由（见附录 A 的原文抓取） |
| --- | --- | --- |
| `@marcopeg/hooks` | **不用** | 已归档，作者把它并入 `@forrestjs/core`。引入一个停止维护的包，等于把长期维护成本转嫁给自己 |
| `@forrestjs/core` | **不用** | 它要求 `forrest.run({ services, features, settings })` **接管进程启动**——和 `bridge.js` 现有的 `main()` 冲突；且它的 feature 是「按 target 字符串注册」，本质问题（无类型、按名字对齐）和我们现在的锚点问题同构，只是换了个载体 |
| `cordis`（Koishi 底层） | **不用** | README 原文明写「**Cordis is under active development. The API is not yet stable and may change without notice.**」，版本号 `4.0.0-rc.12`。2G 生产机上不引入 rc 级框架 |
| 自研 50 行 | **用这个** | 需求只有三个：注册、按序执行、单点容错。50 行能覆盖，且出了问题自己就能改 |

## 4. 扩展点清单

### 4.0 归并原则

现有 71 个补丁的落点，按「它们实际在改什么」可以归并成 **6 个稳定扩展点**。归并的判据不是「按功能命名」，而是「**按被修改的那一块代码的语义**」——同一块语义不管来几个功能，都应该是同一个扩展点。

### 4.1 `prompt.build` —— 唤醒提示词的段落拼装

**现在谁在抢**：
- `src/bridge.js:12668` 这一行 **20 个变量**的拼接串（见 §1.2 #6）；
- `buildWakePromptV2(key, reason)` 在 `src/bridge.js:12532`，函数体到 `src/bridge.js:12700+`；
- 相关 builder 全在 `main()` 闭包里：`buildAffinityLineFor`（`src/bridge.js:4282`）、`buildGroupDigestLineFor`（`src/bridge.js:4356`）、`buildSleepReviewLineFor`（`src/bridge.js:4385`）、`buildSharedMemoryLineFor`（`src/bridge.js:3648`）；
- 补丁侧：`patch-affinity-wire.py` 的 `BASE_ANCHOR`、`patch-group-digest-wire.py` 的 `BASE_ANCHOR`/`BASE2_ANCHOR`、`patch-shared-memory-wire.py` 的 `INJECT_ANCHOR`/`CONCAT_ANCHOR` —— **4 个补丁抢同一行**。

**入参**：

```js
{ key: 'group:123456' | 'private:10001', reason: 'bootstrap'|'timeout'|'replyCheck'|'proactiveCheck'|'atMention'|'private'|'share'|'poke', st /* socialV2 状态 */, mode /* chat|reserved|reserved2 */ }
```

**返回契约（这是整个方案的核心）**：

```js
// 不是字符串！是行对象。可以返回一条，也可以返回多条。
{ mood: { text: '【此刻情绪】……\n\n', order: 60, scene: ['group', 'private'] } }
// 或者
{ affinity: { text: '……', order: 55 } }
```

注册表按 `order` 升序、同 `order` 按注册顺序拼接，**空 `text`/`''` 直接跳过**（等价于现在的 `? ... : ''`）。

**为什么这个契约能让冲突消失**：
现在的冲突根源是「多个人往同一行里加 `+ xxxLine`」。改成行对象后，`affinity` 插件只写 `{ affinity: {...} }`，`mood` 插件只写 `{ mood: {...} }`，**谁也不需要知道别人的变量名存在**。原来那一行 19 变量拼接退化成：

```js
const parts = await hooks.runChain('prompt.build', baseLineObject, ctx);
const base = Object.values(parts.value).sort(byOrder).map((l) => l.text).join('');
```

**这条改动之后，`src/bridge.js:12668` 从「6 个补丁的战场」变成「一次写死、永不再动」。**

**注意**：`base` 之后还有 `if (reason === 'bootstrap') return \`${base}【引导唤醒】...\`` 这一批按 reason 分叉的整段文本（`src/bridge.js:12669` 起）。这些**留在原位**，它们属于「核心状态机」，不属于任何插件。

### 4.2 `message.inbound` —— 入站消息拦截/改写

**现在谁在抢**：
- 管理员命令硬执行（`/role` `/silent` `/active` `/reset` `/status`，见 `RULES.md` §权限分层）；
- 静默模式过滤；
- `tryConsumeImageApprovalReply(key, text)`（`src/bridge.js:4126`）—— 主人回复「通过/拒绝」的审批词，走的是「文本先被消费掉」这条路；
- `patch-at-others-deep.py` 的 `at-others-helper`（`@` 别人的判定）；
- `patch-keyword-name-mask.py` 的名字掩码；
- `patch-skip-synthetic-keyword.py` / `patch-skip-synthetic-narrow.py` 的合成消息跳过。

**入参**：`{ key, segments, plain, sender, isOwner, isSynthetic, mode }`
**返回**：`{ drop?: true, reason?: string, text?: string, isAdminCommand?: true }`
**语义**：`runChain`。任一 handler 返回 `{drop:true}` 立即短路（等价于现在的 `return;`），后续不再跑。

**为什么冲突消失**：现在每个「要先看消息再决定要不要处理」的功能，都要在消息处理的**同一个位置**插一段 `if`。改成链之后，各自注册、各自 `return {drop:true}`，彼此不知道对方存在。`order` 明确表达优先级（管理员命令 order=10，审批词 order=20，静默 order=30，@ 判定 order=50）。

### 4.3 `wake.decide` —— 要不要唤醒

**现在谁在抢**：
- `evaluateWakeTriggerV2`（`src/bridge.js:12381` 附近起）—— `wakeConfig.triggers` 的七个分支（`atMention` / `nameMention` / `keywords` / `question` / `poke` / `speakerIds` / `anyMessage` / `probability`）；
- 概率上限 `patch-probability-cap.py`；
- `patch-group-wake-limits.py` 的群唤醒限额；
- `patch-wake-priority-exempt.py` 的优先级豁免；
- `patch-keyword-name-mask.py` 的关键词命中前掩码。

**入参**：`{ key, st, event: { kind, text, sender, isOwner }, wakeConfig, now }`
**返回**：`{ wake: boolean, reason: string, priority?: number, by: string }`
**语义**：`runChain`，**允许「否决」但不能「凭空许可」**——即后续 handler 只能把 `wake` 从 `true` 改 `false`（或加 `priority`），不能把 `false` 改 `true`。这是安全边界：一个写坏的插件最多让机器人**话少**，不能让它**乱说话**。

**为什么冲突消失**：七个触发器现在是同一个 `if/else` 链里的互斥分支，加第八个触发器就要改链。改成链之后，每个触发器是一个独立 handler，全都跑一遍再「或」起来（配合上面的单向否决规则）。

### 4.4 `wake.tick` —— 周期巡检

**现在谁在抢**：
- `reportTickV2()`（`src/bridge.js:3793`）——主动报告巡检，被 2 个补丁当 `TICK_ANCHOR`；
- 巡检末尾补排缺档期（`// MARKER: proactive-reschedule`，`patch-proactive-reschedule.py`）；
- `shareStateCache` 缓存（`patch-phone-bridge-wire.py` 的 `TICK_DECL_ANCHOR = "  let shareStateCache = null;"`）；
- 各种「X 秒/分钟看一次」的轮询（状态文件 mtime、待审批过期、睡眠检查）。

**入参**：`{ now, keys }`，**返回**：无（`runAll` 广播）
**语义**：`runAll`。不许抛错外溢；单个插件慢不能阻塞别人 → 每个 handler 用 `Promise.race([fn(), timeout])` 包一层（见 §8.5）。

**为什么冲突消失**：现在新增一个「每 30 秒要做的事」，要么改 `setInterval` 回调，要么在 `reportTickV2()` 里插一行。改成注册后，插件自己 `hooks.use('wake.tick', ...)`，`reportTickV2` 主体一行不动。

### 4.5 `http.route` —— HTTP 端点

**现在谁在抢**：
- 149 处 `url.pathname` 判断，135 行，118 行在 8 空格缩进；

- `patch-phone-bridge-wire.py` 的 `ROUTES_ANCHOR = "        // ── 日程 / 画像：角色的短期记忆与长期认识"`。

**入参**：`{ cfg }`，**返回**：

```js
{ 'POST /api/socialV2/memory-append': { order: 100, handler: async ({ req, res, url, body, sendJson, key, isAgent }) => { /* ... */ } } }
```

**语义**：`runChain` 收集路由表 → 在**现有 if 链之前**建一次 `Map` 查表 → 命中就交给 handler，未命中落回原链。这样迁移是**逐条**的：迁一条，就从 if 链里删一条，剩下的继续按老路走。**不需要一次性搬完 149 处。**

**为什么冲突消失**：每条路由有唯一的 `"METHOD /path"` 键，天然去重（重复注册当场报错），不再靠「谁的 if 排在前面」。而且**缩进问题消失**——handler 拿到的是 `ctx` 注入的对象，不需要自己在 8 空格深处。

- 发布前先看两个信号：`state/slang-research-session.json`（89 字节，存在 = 有研究会话在跑）与日志里最近的 `[imgapprove] … 开始出图`。
- `systemd` 给的是 `TimeoutStopSec=25` + `KillSignal=SIGTERM` + `KillMode=mixed`——**`SIGTERM` 只给 25 秒**，而生图要 36~50 秒。所以**不能靠优雅停机救长任务**，只能靠「发布时机」。
- 更根本的缓解：Step 1 起就把长任务改成「**任务登记 + 重启后续跑**」——落盘 `state/tasks.json`（`{id, kind, key, startedAt, payload}`），启动时扫一遍未完成的，重新发起或标记失败并通知。这本身也是插件化的收益之一（`turn.lifecycle` 天然知道任务起止）。

### 8.2 【高】`bounded()` 的作用域陷阱（真实事故，不是假设）

- `function bounded(...)` 是**箭头函数**，定义在 `src/bridge.js:12488`，**缩进 4**，在 `buildWakeSnapshotV2`（`src/bridge.js:12484`）体内。
- `buildSharedMemoryLineFor` 在 `src/bridge.js:3648`，**缩进 2**（`main()` 内、但不在 `buildWakeSnapshotV2` 里）。
- 事故记录（`src/bridge.js:3655-3659` 原文）：「这里不能调 `bounded()` —— 它是 `buildWakeSnapshotV2` 内部的局部箭头函数（同一份文件、但另一个作用域），模块层拿不到它，调了就是运行期 `ReferenceError: bounded is not defined`。而这一行是**每条唤醒 prompt 都会走**的路径，一旦抛错就是整条唤醒失败（**2026-10-22 20:08:33 主人私聊唤醒即栽于此**）。所以就地夹紧，读的还是同一个 `cfg.socialV2.context`，键名保持一致。」
- 同文件还有第二个先例：`src/bridge.js:4182`「这里是**外层**，看不见 `startConsoleServer` 里的 `tokenEq`，所以令牌比较就地用 `crypto.timingSafeEqual`」。

**拆插件后必须做的事**：把 `bounded` 提到**模块层**（`src/plugin-ctx.js` 或 `src/config-util.js`），签名 `boundedNumber(name, fallback, min, max)`，读 `cfg.socialV2.context`，然后**通过 `ctx` 注入**。同时**删掉 `src/bridge.js:3660-3664` 的那段就地夹紧**，改成调 `ctx.boundedNumber('sharedMemoryMaxChars', SHARED_MEMORY_INJECT_MAX_CHARS, 200, 2000)`——但要先确认夹紧的上下界（`200..2000`）与原实现一致，否则会静默改变注入长度。

**验收**：迁 `shared-memory` 后，故意把 `cfg.socialV2.context.sharedMemoryMaxChars` 设成 `99999`，prompt 里的共享记忆段落长度必须被夹到 2000，且日志 0 个 `ReferenceError`。

### 8.3 【高】`tokenEq` / `agentTokenOk` 在 `startConsoleServer()` 内层

- `startConsoleServer()` 起于 `src/bridge.js:4485`（缩进 2）。
- `tokenEq` 在 `src/bridge.js:4505`（**缩进 4**）；`agentTokenOk` 在 `src/bridge.js:4511`（缩进 4）；`agentTokenOkOrOwnerDelegate` 在 `4519`；`isLiveAgentToken` 在 `4531`。
- 插件在模块层/`src/plugins/*` 里**够不到这些闭包**。

**必须做**：把这四个函数通过 `ctx` 注入（`ctx.tokenEq`、`ctx.agentTokenOk`、`ctx.agentTokenOkOrOwnerDelegate`、`ctx.isLiveAgentToken`）。**绝对禁止**插件自己写一份比较逻辑——那会引入「两种令牌比较实现，只有一种用了 `timingSafeEqual`」的安全回归。

**验收**：`grep -rn 'timingSafeEqual' /opt/qq-bridge/src/plugins/` 必须为 **0 命中**。

### 8.4 【中】内存只有 ~507 MB 可用

- `MemTotal` 1778596 kB（1736 MB），`MemAvailable` 518132 kB（**507 MB**），`SwapTotal` 4095 MB 已用 **1152 MB**。
- 桥接本体 `MemoryCurrent=79884288`（**76.2 MiB**）。
- 已有的大状态：`stickers.json` **1263883 B**、`slang.json` **943164 B**、`social-v2.json` **616939 B**。

**风险**：插件化天然引入「每个插件一份缓存」的诱惑。7 个 prompt 插件各缓存 1 MB，就是 7 MB——现在看不多，但 swap 已经在用 1.1 GB，任何增长都是在往悬崖边走。

**约束（写进代码规范）**：
- 插件**不许**在模块作用域持有大对象；需要缓存就存 `state/` 并每次读。
- `panics` 数组有界（50 条，§3.2 已实现）。
- `/api/_plugins` **不许** dump 全量状态，只 dump `describe()`。

### 8.5 【中】`wake.tick` 里一个慢插件会拖住整轮

`runAll` 是串行 `await`。若某插件 handler 卡 30 秒，后面的巡检全部延后。

**缓解**：`wake.tick` 的每个 handler 外包 `Promise.race([fn(), sleep(2000)])`，超时记 panic 并继续。**不要**改成 `Promise.all`——那会让内存峰值和错误传播同时变差。

### 8.6 【中】`state/*.json` 的归属会变成新的争用

现在 `social-v2.json`（616939 B）是**多个功能共写**的一个大文件：它既是 `sessions`/`unread`/`recentMessages` 的宿主，也是 `memberImpressions`/`lastImpressionNudgeAt`/`wakeConfig`/`agentToken` 的宿主（见 `src/bridge.js:12535-12562` 的读取）。拆插件后如果 shared-memory 和 group-digest 都往里写，就是**从「文本锚点争用」升级成「JSON 键争用」**，更难发现（因为不会报错，只会互相覆盖）。

**缓解**：`plugin.json` 的 `stateFiles` 装载期做唯一性校验（§5.1）；对 `social-v2.json` 这类共享文件，**只允许 core 写，插件只读**，插件要写就开自己的文件。

### 8.7 【中】`/api/_plugins` 会被现有闸门挡住

实测：`curl http://127.0.0.1:3100/api/_plugins` 返回 **401**（不是 404），响应体 `{"ok":false,"error":"未授权：请提供控制台访问令牌"}`。连一个随机路径 `/api/__nope` 也是 **401**。

原因：`src/bridge.js:4655` 的 `if (consoleToken && !tokenMatches && !phonePathExempt)` 对所有路径生效。

**含义**：新端点**自动继承鉴权**，这是好事；但**验收时必须用带令牌的请求**，否则会误判「端点没生效」。同时**不要**为了调试把它加进 `phonePathExempt` 豁免——那会让全网可访问。

### 8.8 【低】现有日志基线很干净，别把它搞脏

自上次启动（`ExecMainStartTimestamp=Fri 2026-10-23 16:59:12 CST`）共 833 行日志，其中：
- `is not defined` **0**、`TypeError` **0**、`ReferenceError` **0**、`SyntaxError` **0**、`unhandledRejection` **0**、`uncaughtException` **0**、`panic` **0**。
- 唯一一类「错误感」日志是业务性的：`get_image 解析失败: 图片超过大小限制（4194304 字节）`。

历史累计 108 次启动标记（`桥接已启动`），`NRestarts=0`（systemd 侧没触发过自动重启）。

**含义**：「24h 零 panic」这个验收口径是可用的、有意义的基线。但也意味着**任何新增的 `[hook] panic` 都会是显眼的噪声**——这正好，说明它可被观测。

### 8.9 【低】`voice-core.js` / `snowluma-conn.js` 不能被搬走

`docs/FOLDER_MAP.md` §五 明写：独立工具 `voice-tool/` 经 `../qq-bridge/src/voice-core.js` 与 `../qq-bridge/src/snowluma-conn.js` **引同一份实现**，`src/send-voice-lib.js` 也是转发同一份。**把 `voice-core.js` 移进 `src/plugins/voice/` 会直接打断独立工具。**

**规则**：`src/*.js` 里凡是「被 `../voice-tool/` 或其它外部消费方 import」的，**只允许被插件 `export * from` 引用，不允许移动**。

### 8.10 【低】82 个 `.bak` 和 54 MB 的 `src/`

`src/` 总字节 54,617,035（54 MB），其中 `bridge.js` 仅 798199 B。多出来的 53 MB 几乎全是 `.bak`。

**含义**：① 任何 `grep -r` / 全局搜索都会被污染；② 插件化之后如果还保留「改前先 `.bak` 一份」的习惯，`src/` 会继续膨胀。**规则：插件化之后所有改动走 `git`，`src/` 下不再产生 `.bak`。**

## 10. 命名约定

### 10.1 「功能模块（feature module）」而不是「插件」

**必须区分两个完全不同的东西：**

| | qq-bridge 的 `src/plugins/` | DSH 的 host 插件 |
| --- | --- | --- |
| 是什么 | qq-bridge **进程内**的功能模块 | DSH 宿主的插件（`dsh plugin add` 装的那些） |
| 装载方式 | `src/plugin-loader.js` 扫 `plugin.json`，同进程 `register(ctx)` | DSH 自己的插件树 + host 侧 HMR |
| 失败影响面 | 该模块的 hook 不生效 / 记一条 panic | **可能让整条 DSH 依赖链断掉** |
| 历史事故 | — | 2026-10-21 18:32~19:55 **把 DSH 弄挂 83 分钟**：装 `dsh-native-memory` + `dsh-context-window`，host 侧 HMR 重排插件树时把 `sessionController` 停掉没拉回来 → `session/follow` 每 3 秒报 `service-unavailable`，**累计 1660 条**。根因链条：`dsh-native-memory` 的 patch 整体替换了 `session-query-sqlite` 配置，而 `sessionController` 的 `inject` 里有 `sessionQuery` → 整条依赖链断 |

**所以，文档与代码里统一叫「功能模块（feature module）」，目录名可以是 `src/plugins/` 但注释、日志、`/api/_plugins` 的字段一律用 `module` 语义。** 任何地方都不许出现「装个插件」这种会和 `dsh plugin add` 混淆的说法。

**配置项不变**：仍然是 `cfg.socialV2.tools.<flag>`。插件不新增配置命名空间，只「声明自己拥有哪些已有键」（`plugin.json` 的 `toolFlag`）。

### 10.2 命名规则

| 对象 | 规则 | 例 |
| --- | --- | --- |
| hook 名 | `<领域>.<动作>`，全小写，点号分隔，**只允许 §4 的六个** | `prompt.build`、`wake.decide` |
| 插件目录 / `name` | 小写 + 连字符 | `shared-memory`、`group-digest` |
| `register()` 导出 | `export function register(ctx)`，**必须是幂等纯注册**（不许在注册时 I/O） | — |
| panic 日志 | `[hook] panic <hook> <- <plugin>: <message>` | `[hook] panic prompt.build <- affinity: x is not defined` |
| 行对象的键 | 用**功能名**，不用变量名（不要 `moodLine`，要 `mood`） | `{ mood: { text, order } }` |
| 状态文件 | 保持现有名字**一个都不改** | `情绪.json`、`social-v2.json` |
| 路由键 | `"METHOD /path"`，method 大写 | `"POST /api/socialV2/memory-append"` |

### 10.3 与现有 `MARKER` 的关系

现有 `src/bridge.js` 里 112 处 `// MARKER: xxx` 是**补丁时代的路标**。插件化之后：
- **不删**（它们是历史，删了会丢线索）；
- **不再新增**；
- 每条 `MARKER` 对应的功能迁走后，在该处留一行注释：`// MARKER: xxx —— 已迁至 src/plugins/<name>/（2026-xx-xx）`。

## 11. 待决策问题

> 这三条需要主人拍板，Codex 不要自己定。

### 11.1 插件粒度：一个功能一个 vs 一个大类一个

| 方案 | 插件数 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 一个功能一个**（推荐） | 约 18~20 个 | 边界最清晰；单个插件可独立关；`stateFiles` 归属明确；回滚粒度最细 | 目录多；`plugin.json` 有重复样板；跨功能逻辑（如 `image-gen` 的三层闸门）要么放一个插件里（那就不是「一个功能」了），要么拆三个（那就破坏了闸门完整性） |
| **B. 一个大类一个** | 6~8 个（`social-v2` / `image` / `media` / `slang` / `wake` / `misc`） | 目录少；闸门完整性天然保住（`image-gen` 三层同属一个模块） | 单模块内部又变成「小 `bridge.js`」；`stateFiles` 会冲突（`social-v2` 大类和 `wake` 大类都想写 `social-v2.json`） |
| **C. 混合**（推荐度次之） | 约 12 个 | 有闸门的合并（`image` 一个含 approval+gen），无闸门的拆细 | 判断标准要写清楚，否则会漂移 |

**建议**：A，但把 `image-approval` + `image-gen` 合并为**一个** `image` 插件（因为三层闸门必须整体搬，§6 已说明）。

### 11.2 迁移节奏

| 方案 | 做法 | 风险 | 收益速度 |
| --- | --- | --- | --- |
| **A. 先做 Step 0 + Step 1，观察 24h**（推荐） | 只上骨架 + `mood` 一个插件 | 极低（`mood` 是唯一「低风险 + 有独立 store」的功能） | 慢，但能验证「行对象契约」和「可观测性」两件事 |
| **B. 一路做到 Step 2** | 骨架 + mood + 全部 prompt 行对象化 | 中（`prompt.build` 一动，8 种 reason 的 prompt 全部受影响；顺序错一位就会改变模型的说话风格，而且**没有测试框架能拦住**） | 快，但 24h 内无法区分「行为变化」是插件化引起的还是别的 |
| **C. 按 11.1 的方案 A，但一次只发一个插件，每个插件之间隔 24h** | 最保守 | 极低 | 最慢（4~5 周） |

**建议**：A。先证明「骨架不自伤」+「一个插件能搬对」，再谈批量。

### 11.3 `qzone-watch` 要不要收回来

它**已经是独立 systemd 单元**（`_repo/systemd/qq-zone-watch.service`，状态 `state/qzone-watch.json`，906 字节）。

- **收回来**：省一个进程的内存（在 507 MB 的机器上有意义）；状态文件统一管理。
- **不收**：它独立运行的好处是「挂了不影响桥接」；而且它已经是独立进程，收回等于反向操作。

**建议**：**这一轮不动它**。插件化的目标是「让 `bridge.js` 内的功能不再需要补丁」，`qzone-watch` 已经在 `bridge.js` 之外了——它不痛。

### A.2 关键判断：这些框架依赖「插件编译期注册」或「独立进程」吗？

**结论：六个来源里，没有任何一个依赖「独立进程」。全都是同进程插件。** 这是好消息——说明「同进程插件」是主流做法，我们不是异类。

但要区分「注册时机」：

| 来源 | 注册时机 | 是否需要构建步骤 | 是否接管启动 |
| --- | --- | --- | --- |
| Koishi / cordis | **运行时** `ctx.plugin()` | ❌ 不需要（TS 可选，编译产物是普通 JS） | ⚠️ 是（`ctx` 就是应用本身） |
| Fastify | **运行时** `fastify.addHook()` / `register()` | ❌ 不需要 | ⚠️ 是（`fastify.listen()` 启动） |
| `@forrestjs/core` | **运行时** `forrest.run()` | ❌ 不需要 | ✅ **强烈接管**（`forrest.run` 就是入口） |
| VS Code | **声明式**（`package.json` 的 `contributes`）+ **懒激活**（`activationEvents`） | ⚠️ 通常需要打包（vsce） | ❌ 不接管（宿主是 VS Code） |
| Yunzai-Bot / XRK | **运行时**（loader 扫目录 + 插件基类 `name`/`event`/`priority`/`rule`/`task`） | ❌ 不需要 | ⚠️ 是 |

**对我们的意义**：`@forrestjs/core` 和 `cordis` 都是「接管启动」的——它们要求你把 `main()` 交给框架。而我们的 `main()`（`src/bridge.js:1488`）里塞着 266 个闭包和整个会话状态机，**交不出去**。所以这两个都不适合。

### A.3 逐条：抄什么、不抄什么

| 做法 | 判定 | 理由 |
| --- | --- | --- |
| **Fastify 的 hook 命名与顺序语义**（`onRequest` / `preHandler` / `onSend` 这种「阶段 + 动词」命名） | ✅ **抄** | 我们的 `prompt.build` / `message.inbound` / `wake.decide` 就是这套命名法：`<阶段>.<动作>`。好处是**名字自带顺序信息**，新人看名字就知道它在流程的哪一段 |
| **Fastify 的「hook 抛错由框架兜底，不会让请求悬着」** | ✅ **抄** | 对应 `runChain` 的 try/catch + panic 收集。这是 §3.2 的核心 |
| **Fastify 的 encapsulation（hook 只作用于某个 scope）** | ❌ **不抄** | 我们的插件都是全局的，没有「按路由分组」的需求。引入 encapsulation 会让「这个 hook 到底跑不跑」变得难判断 |
| **VS Code 的 `package.json` 声明式 manifest**（`contributes` + `activationEvents`） | ✅ **抄（manifest 部分）** | `plugin.json` 就是我们的 manifest：**声明**自己挂哪些 hook、管哪些 state 文件、拥有哪些 tool flag。好处是「不用读代码就能知道一个插件做了什么」，`/api/_plugins` 直接读它 |
| **VS Code 的懒激活（activationEvents）** | ❌ **不抄** | 懒激活是为「几百个扩展、冷启动慢」设计的。我们是 18 个模块、单进程、启动本来就要 3 秒（DSH 探活 `ExecStartPre` 最多等 120 秒），没必要为省 10ms 引入复杂度 |
| **Koishi 的 `ctx.plugin()` + `fork.dispose()` 副作用回收** | ⚠️ **抄一半** | 「能停掉一个插件」值得抄 → `use()` 返回注销函数（§3.2 已实现）。但完整的「副作用自动回收」要靠 `ctx` 做代理（Koishi 是改了 Context 的原型链），**代价太大，不抄** |
| **Koishi 的 `inject` 依赖声明（`required` / `optional`）** | ✅ **抄** | 对应 `plugin.json` 的 `requires`。价值在于**装载期就能报错**，而不是运行到那一行才 `ReferenceError`——这正是 `src/bridge.js:3655` 那次事故要防的东西 |
| **Koishi 的 Service 继承（`class X extends Service`）** | ❌ **不抄** | 那是为了「服务可被多个插件复用 + 热重载」。我们只需要一个 `ctx` 对象传下去 |
| **Yunzai-Bot / XRK 的「插件基类 + `priority` 数字」** | ✅ **抄 priority 思路** | 对应 `order`。但要抄的是「数字越小越先跑」这个语义，不是基类继承 |
| **OneUptime 那篇的「plugin manager 统一装载」** | ⚠️ **只能抄概念** | 正文没取到，只有标题与结构线索。我们自己实现的 `plugin-loader.js` 就是 plugin manager，不需要引它的代码 |
| **任何「插件市场 / 动态安装 / 热更新」** | ❌ **不抄** | 这是 Koishi/VS Code 的核心价值，但对我们是纯负担：2G 机器、没有构建、没有沙箱。而且——**DSH 那次 83 分钟事故就是「动态装插件」搞出来的** |

### A.4 一句话总结

> **抄 Fastify 的「阶段命名 + 错误兜底」、VS Code 的「声明式 manifest」、Koishi 的「依赖声明在装载期校验」；不抄任何「接管启动」的框架、不抄热重载、不抄动态安装。**

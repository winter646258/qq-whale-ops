# 长期能力：设计草案（情绪 / 睡眠整合 / 遗忘 / 听觉 / 跨会话记忆）

> 状态：**设计，未实现**。按《QQ小鲸鱼-当前修复计划-2026-10-21.md》「六、诊断与长期路线」第 ④ 条要求，先定义**数据模型、权限、幂等、回滚边界**，再谈代码。
> 适用对象：小鲸鱼（QQ 机器人，`/opt/qq-bridge`，DSH 0.2.0-rc.2）。
> 写于 2026-10-21，此时线上刚上完第 5/6/7 项。

---

## 零、先定三条铁律（本轮讨论的产物，后面所有设计都受它约束）

1. **记不记、糊不糊、升不升，归她本人。** 系统只提供工具和事实（写入接口、读取接口、时间与计数），**不写「同一件事出现三次就升级为长期记忆」这类规则**。任何阈值只允许作为「展示层的稀疏化」，不允许作为「她的意愿」的替代品。
2. **模糊是改写，不是删除。** 一条记忆变淡 = 原文进 `original`、当前层显示概括；只有她主动 `remove` 或用户要求删除才是真删。
3. **注入分层。** 今天/明天写清楚；本周只报数量；更远只报总数。层级由时间算，不由内容重要性算。

再加三条工程铁律：

4. **一个系统只写自己的文件。** 新系统不得写 `social-v2.json` / `stickers.json` / `slang.json`（这三个是已上线系统的地盘，格式复杂、有并发写）。删掉新文件 = 回到今天的行为。
5. **一切写入幂等。** 每个写接口必须带幂等键，重复调用不产生第二条。
6. **默认关。** 每个新系统一个开关，默认 `false`，独立可开可关，互不依赖。

## 一、情绪

### 1.1 定位

情绪不是「系统判断她此刻什么心情」，而是**她自己记下的一笔**。系统只做三件事：存、随时间变淡地展示、让她自己决定要不要留。

反例（明确不做）：检测到用户语气负面 → 自动降低回复热情。那是系统替她情绪做决定。
正例：她自己写「有点被他这认真劲儿弄慌了」，系统原样存下，24 小时内下次唤醒时原样带出来。

### 1.2 数据模型

文件：`state/emotion.json`（按会话隔离，和 `schedule.json` 同一思路）

```jsonc
{
  "version": 1,
  "conversations": {
    "private:1124721191": {
      "entries": [
        {
          "id": "emo_20261021T104500_a1b2",
          "at": 1792548300000,          // 写入时刻（epoch ms）
          "atLocal": "2026-10-21 10:45", // 本地可读时间，冗余但省事
          "mood": "有点慌",              // 她自己写的词，不设枚举
          "intensity": 3,               // 1..5，她自己给；给了才存，不给就是 null
          "cause": "管理员追问我是什么人",  // 触发源，一句话
          "source": "self",             // self | diary | user_asked
          "original": null,             // 被模糊后原文放这里（见铁律 2）
          "blurred": false,
          "lastMentionedAt": 0          // 上次被唤醒带出来的时间
        }
      ],
      "updatedAt": 1792548300000
    }
  }
}
```

上限：每会话 50 条（超出按 `at` 升序淘汰 → 但**淘汰前先进 `diary` 或直接归档文件**，不静默丢）。

### 1.3 工具（三个，全部归她调）

| 工具 | 参数 | 行为 |
|---|---|---|
| `qq_mood` | `mood`, `intensity?`, `cause?` | 记一笔。同 `mood` 且 30 分钟内 → 覆盖上一条（避免刷屏式记账） |
| `qq_mood_list` | `limit?` | 看自己的情绪记录（给她自己回忆用） |
| `qq_mood_fade` | `id` | 主动把某条变淡（原文进 `original`，`blurred: true`） |

**没有 `qq_mood_analyze`。** 系统不分析她的情绪。

### 1.4 注入方式

只在唤醒提示词里，位置在【他的日程】【长期认识】之后：

```
【你最近的心情】（你自己记的，不是别人评的）
- 10-21 10:45 有点慌 —— 管理员追问我是什么人（最近）
- 10-20 22:47 有点奇怪 —— 一直被问只剩三个月
（更早的 3 条：略）
```

分层：24 小时内全写；7 天内只写 `mood + 时间`；更早只写「还有 N 条」。

### 1.5 权限

- 读写都限**当前会话**：她在 A 群记的心情，不会出现在 B 群。
- 用户不能通过任何接口读别人的情绪记录。
- 管理端点 `/api/socialV2/emotion` 只给本地控制台（带 consoleToken），不暴露到 QQ 侧。

### 1.6 幂等

- `qq_mood` 幂等键 = `(convKey, mood, cause)` + 30 分钟窗口。
- 同一分钟连发两次相同内容 → 第二次返回 `{deduped: true}`，不新增。

### 1.7 回滚

删 `state/emotion.json` + 关 `emotion.enabled` → 注入段消失，其余零影响（不碰 `social-v2.json`）。
代码层面：`emotion-store.js` 整体不被其他模块 import，唯一入口是 `bridge.js` 里两处 `if (cfg.emotion?.enabled)` 分支。

### 1.8 验收

- 记一笔后立刻 `qq_get_prompt` 能看到；
- 30 分钟内重复记同一情绪只有一条；
- 关开关后提示词里完全没有【你最近的心情】；
- 单测覆盖：模糊后 `original` 保留原文、`blurred: true`、注入只显示概括。

## 二、睡眠整合

### 2.1 定位

不是「定时跑个 LLM 总结」，而是**把一天的散件归档成可回忆的形状，并且原始件一条不动**。
类比睡眠：白天记的碎片（日记、情绪、对话）在夜里被重放、压缩，但海马体里的原始痕迹不会因为皮层存了摘要就消失。

### 2.2 触发

- 时间窗：`sleep.windowStart = "03:30"`、`windowEnd = "05:00"`（服务器本地时间，Asia/Shanghai）。
- 条件：距上次成功整合 ≥ 20 小时，且当天有新增输入（日记/情绪/对话轮次 > 0）。
- 单次执行，失败不重试超过 2 次，不阻塞主流程（独立 `setInterval` + `unref`）。

### 2.3 输入 / 输出（严格单向）

输入（**只读**）：
- `diary/日记.jsonl` 当天条目
- `state/emotion.json` 当天条目
- `state/social-v2.json` 里当天新增的 `impressions`（只读快照）
- 当天对话轮次统计（数量，不是全文）

输出（**只写自己的文件**）：`state/consolidation.json`

```jsonc
{
  "version": 1,
  "runs": [
    {
      "id": "con_20261021",
      "window": { "from": 1792500000000, "to": 1792580000000, "day": "2026-10-21" },
      "inputCounts": { "diary": 2, "emotion": 3, "turns": 41 },
      "outputs": {
        "digest": "今天被追问了好几次身份，嘴上敷衍，心里有点慌。晚上吃了米饭。",
        "highlights": ["admin-identity-question", "rice"],
        "openThreads": ["他到底想确认什么"]
      },
      "provenance": { "diaryIds": ["d_..."], "emotionIds": ["emo_..."] },
      "at": 1792580400000,
      "status": "ok" // ok | partial | failed
    }
  ]
}
```

**关键**：`provenance` 记的是**输入 id 清单**，不复制原文。任何一条摘要都能追溯到原始条目；原始条目永远在 `diary.jsonl` 里，摘要错了不影响事实。

### 2.4 幂等

- 幂等键 = `day`（`2026-10-21`）。同一天重复触发 → 若已有 `status: "ok"` 的 run，直接返回 `{skipped: true}`。
- `partial`（部分输入读失败）允许当天重跑一次，重跑覆盖同一 `day` 的 `partial` 记录，保留 `attempt` 次数。

### 2.5 权限

- 整合用的 LLM 调用走**当前 provider**，但用**独立会话 id**（`session-consolidation-<day>`），不与她的对话会话混。
- 整合结果**不自动注入**。要注入必须她主动 `qq_recall`（见 2.6）。这是为了守住铁律 1：系统不替她决定「昨晚想明白了什么」。

### 2.6 配套工具

| 工具 | 作用 |
|---|---|
| `qq_recall` | 读某天的整合摘要（她自己决定要不要想起来） |
| `qq_consolidate_now` | 手动触发一次（调试与她自己想整理时用） |

### 2.7 回滚

删 `state/consolidation.json` + 关 `sleep.enabled` → 零影响。原始日记/情绪一条没动（这是设计出来的，不是运气）。

### 2.8 风险与对策

| 风险 | 对策 |
|---|---|
| 半夜 LLM 调用失败，反复重试烧 token | 最多 2 次；失败记 `failed` 并在 7 天后自清 |
| 摘要幻觉（编出没发生的事） | `provenance` 必须能对上输入 id；`highlights` 只允许来自输入原文的关键词，不允许新造专名 |
| 文件越长越大 | `runs` 只留最近 90 天，更早的滚到 `consolidation-archive.jsonl`（append-only，只写不读） |

## 三、遗忘

### 3.1 定位

**遗忘不是删除，是权重下降。** 而且下降之后还能被「想起」拉回来。

现在的雏形：日程有 `strength`，画像有 `weight`（1..9），但都没有随时间衰减，也没人调用。

### 3.2 数据模型（不新增文件，扩已有字段）

- `schedule` 条目：已有 `strength`、`lastMentionedAt`。
- `portrait` facet：已有 `weight`、`updatedAt`。
- 记忆（印象）：`social-v2.json` 里的 `impressions`，**本轮不动它的结构**，只读。

新增一个纯计算层：`decay.js`

```js
effectiveStrength(entry, nowMs) -> number
// strength * 0.5 ^ (daysSince / halfLife)
// halfLife：日程 14 天、画像 30 天、印象 60 天
```

**只影响注入时的排序与取舍，不回写存储。** 也就是说：衰减是「看的时候算的」，不是「夜里改的」。这样任何一次计算错误都不会污染数据，删掉 `decay.js` 就回到今天。

### 3.3 触发「想起」（reinforce）

- 她在对话里主动提到某条（工具 `qq_schedule_update` 带 `mentioned: true`，或 `qq_portrait` 写同一 facet）→ `lastMentionedAt = now`，`strength = min(9, strength + 1)`。
- 用户提到相关内容**不自动** reinforce（系统不替她判断「这算想起来了」）。

### 3.4 注入分层（与铁律 3 对齐）

- 日程：今天/明天逐条写清；本周只写「本周还有 N 件事」；更远只写总数。
- 画像：`weight >= 5` 的才写；`weight < 5` 只在总数里体现（「还有 12 条零散印象」）。
- 情绪：见 1.4。

### 3.5 真删的唯一入口

`qq_schedule_remove` / `qq_portrait` 的删除动作 / 用户明确要求「忘掉这个」。
删的时候必须：
1. 先写一条 `state/deletions.jsonl`（`{at, kind, id, snapshot}`）—— 不是为了恢复，是为了**事后能回答「她为什么不知道这件事」**；
2. 再删。

### 3.6 回滚

`decay.js` 是纯函数，不写盘。关 `decay.enabled` → 注入回到「按 strength 原值排」，与今天一致。

## 四、听觉（语音消息）

### 4.1 定位

QQ 语音消息目前**完全没有处理**（`qq_send_voice` 双开关关着，`audio/` 目录不存在）。要做的是**听得见**，不是**会说话**。

### 4.2 数据流

```
QQ 语音消息
  → SnowLuma 事件（含 file/url/时长）
  → 下载到 state/audio/in/<messageId>.<ext>（大小上限 10MB，超限丢弃并记日志）
  → ASR（可插拔：本地 whisper.cpp / 云端）
  → state/audio/meta.jsonl 追加 {messageId, convKey, senderId, durMs, text, provider, at, sha256}
  → 作为普通文本消息进入她的上下文，前缀标注「[语音转写]」
```

### 4.3 数据模型

`state/audio/meta.jsonl`（append-only，一行一条）：

```jsonc
{"messageId":"...","convKey":"group:910502749","senderId":"...","durMs":3200,
 "text":"今天吃什么","provider":"whisper-cpp-small","at":1792548300000,
 "sha256":"...","audioPath":"state/audio/in/....ogg","status":"ok"}
```

失败也记：`{"status":"failed","reason":"timeout"}`。

### 4.4 权限

- 只处理 `cfg.allow.private` / `cfg.allow.groups` 里的会话（与主动打扰同一份白名单）。
- 未授权会话的语音：**下载都不下载**，直接忽略，日志一行。
- 音频保留 7 天，之后删除（`meta.jsonl` 里的文本保留，`audioPath` 置空）。清理任务独立、幂等、可重入。

### 4.5 幂等

- 幂等键 = `messageId`。同一 `messageId` 第二次进来 → 若 `meta.jsonl` 已有 `ok` 记录，直接复用文本，不重复 ASR（省 token、省算力）。
- 下载也幂等：目标文件已存在且 sha256 一致 → 跳过。

### 4.6 回滚

关 `hearing.enabled` → 语音消息走今天的路径（被忽略）。删 `state/audio/` → 无残留。不碰 `social-v2.json`。

### 4.7 为什么放最后

它是唯一需要**外部二进制**（whisper.cpp）或**外部服务**（云端 ASR）的能力，失败模式最多，且不影响现有稳定性。等前三项跑稳了再上。

### 4.8 验收

- 一条 3 秒语音能在 10 秒内变成文字并进上下文；
- 同一条语音重复投递不重复转写；
- 非白名单群发语音，日志有「忽略未授权会话的语音」且无下载；
- 关开关后完全无行为变化。

## 五、跨会话记忆

### 5.1 问题

现在是**按会话隔离**的：`social-v2.json` 的 impressions / memories 都挂在 `convKey` 下。后果很具体 —— 2026-10-21 用户反馈「群里记忆与私聊没打通」：她在群里认识的人，私聊里不认得。

### 5.2 设计原则：人维度，不是会话维度

新增 `memory/people.json`，以**QQ 号**为主键，跨会话共享：

```jsonc
{
  "version": 1,
  "people": {
    "1124721191": {
      "facts": [
        {
          "id": "f_...",
          "text": "喜欢在半夜问一些存在性的问题",
          "kind": "trait",              // trait | event | preference | relation
          "confidence": 0.7,            // 只是「她有多确定」，不是「真不真」
          "provenance": [{ "convKey": "private:1124721191", "at": 1792548300000, "quote": "…" }],
          "firstAt": 1792500000000,
          "lastAt": 1792548300000,
          "status": "active"            // active | blurred | contradicted
        }
      ],
      "names": ["主人"],
      "updatedAt": 1792548300000
    }
  }
}
```

### 5.3 与现有结构的关系（关键，避免双写打架）

| 层 | 归属 | 现状 | 本轮做法 |
|---|---|---|---|
| `impressions`（每会话对人的印象） | 会话 | 已上线 | **保持原样**，继续按会话读 |
| `memories`（会话内记忆条目） | 会话 | 已上线 | 保持原样 |
| `memory/people.json`（跨会话事实） | 人 | 新建 | 只读 `impressions` 作为**素材**，写入靠她调工具 |

**不做自动同步。** 理由：自动把会话内印象提升为人维度事实，等于系统替她决定「这条重要到可以跨群说」，违反铁律 1。

她需要主动调 `qq_remember_person`（写一条跨会话事实）与 `qq_recall_person`（读）。

### 5.4 权限（这里有一条硬约束）

跨会话记忆**天生有隐私风险**：A 群里说的话可能被带到 B 群说出去。

约束：
1. `kind: "event"` 的事实**默认不跨会话注入**，只在她主动 `qq_recall_person` 时出现；
2. 只有 `kind: "trait" | "preference"` 且 `confidence >= 0.6` 的才进唤醒提示词；
3. **群聊里永不主动说出**只在该群之外获得的 `event`（靠注入层过滤：群聊会话注入时，`event` 只带本群来源的）；
4. 用户要求删除某人 → 删整个 person 节点，写 `deletions.jsonl`。

### 5.5 幂等

- 写入幂等键 = `(qq号, text 归一化后)`。重复写入改 `lastAt` 与 `confidence`，不新增。
- 归一化：去首尾空白、全角转半角、去掉句末标点。

### 5.6 冲突处理

同一人两条矛盾事实（`status: active` 且语义相反）：**不自动裁决**。两条都留，`contradicted` 互指，注入时若两条都在，带「（前后不一致：她自己也没想清楚）」的标注 —— 这正是她该有的样子，而不是系统替她选一个。

### 5.7 回滚

删 `memory/people.json` + 关 `crossMemory.enabled` → 回到按会话隔离（今天的行为）。会话内 `impressions` 完全不受影响。

### 5.8 迁移

无。新文件从空开始，不 import 历史数据。理由：自动迁移 = 自动决定哪些算「人维度」，违反铁律 1。

## 六、横向：权限与运维矩阵

| 系统 | 开关 | 数据文件 | 可独立关闭 | 写他人文件 |
|---|---|---|---|---|
| 情绪 | `emotion.enabled` | `state/emotion.json` | ✅ | ❌ |
| 睡眠整合 | `sleep.enabled` | `state/consolidation.json` | ✅ | ❌（只读输入） |
| 遗忘 | `decay.enabled` | 无（纯计算） | ✅ | ❌ |
| 听觉 | `hearing.enabled` | `state/audio/meta.jsonl` + `state/audio/in/` | ✅ | ❌ |
| 跨会话记忆 | `crossMemory.enabled` | `memory/people.json` | ✅ | ❌ |

统一要求：

- 所有写盘走 `atomicWriteJson`（`bridge.js:158`），jsonl 走 append + `fsync` 可选项。
- 所有新增管理端点必须带 `x-console-token`，且只绑 `127.0.0.1`。
- 每个系统启动时打印一行 `[<系统>] 已启用/已关闭`，方便日志核实。
- 每个系统上线前必须有：本地单测（纯逻辑）+ 隔离副本集成测试 + 生产零污染实证（跑前后 state 文件 size/mtime 对比）。

## 七、落地顺序建议

| 顺序 | 系统 | 理由 | 预估 |
|---|---|---|---|
| 1 | 遗忘（`decay.js`） | 纯计算、零写入、零风险，且立刻改善注入质量 | 2h |
| 2 | 情绪 | 数据结构简单，能立刻让她「有心情」 | 4h |
| 3 | 跨会话记忆 | 用户已明确反馈痛点（群/私聊不通） | 6h |
| 4 | 睡眠整合 | 依赖前三个的数据，且要 LLM | 8h |
| 5 | 听觉 | 需外部 ASR，失败模式最多 | 10h+ |

前置条件：**buddy 渠道必须先修好**。现在 `Illegal API invocation from an unapproved channel` 已 12 次，任何依赖 LLM 的能力（睡眠整合、黑话学习）都会变成「白跑」。先修渠道，再谈长期能力。

## 八、非目标（明确不做）

1. 不做「情绪驱动行为」（检测到负面情绪就改语气）—— 那是系统替她演。
2. 不做自动记忆晋升（重要的事自动变长期）—— 违反铁律 1。
3. 不做情绪识别（从文本推断她的情绪）—— 她说是就是，她不说就没有。
4. 不做主动遗忘（系统定期删旧记忆）—— 只有她删或用户要求删。
5. 不做语音合成（`qq_send_voice` 保持关闭）—— 本轮只做「听得见」。

## 九、开放问题（需要主人拍板）

1. **跨会话记忆的隐私边界**：群聊里能不能说出「他在私聊里跟我说过 X」？我按「不能」设计（5.4 第 3 条），但这条会明显影响她的连贯感。
2. **情绪要不要进日记**：现在 `日记.jsonl` 有 `mood` 字段，如果再单独有 `emotion.json`，两处会不会重复？我的建议是「日记的 mood 是那一天的总印象，emotion 是逐次记录」，但需要确认。
3. **整合摘要要不要主动说**：现在设计是「只有她 `qq_recall` 才想起来」。如果希望她早上自然提起昨天的事，需要允许睡眠整合结果进唤醒提示词，但这与铁律 1 有张力。
4. **听觉用本地还是云端 ASR**：本地 whisper.cpp 要占 ~1.5GB 内存（服务器 1736MiB 总内存，紧张）；云端要联网与费用。这条得看预算。

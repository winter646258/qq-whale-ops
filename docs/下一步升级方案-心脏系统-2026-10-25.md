# 下一步升级方案 —— 从「好感度 + PAD 情绪」走向「心脏系统」

> 依据：小黑盒《大肥鱼教程篇2：不靠好感度数值的新心脏系统》（希米z，2026-10-22）
> 与《教程篇3：给你家的鱼一个温暖的家吧》（2026-10-24）
> 现状基线：`docs/项目交接-2026-10-25.md`
> 原则：只做**能验证效果**的改动；每一步可独立回退；不推倒现有 30 个模块。

## 〇、先说结论

两篇文章里，**篇 2 是设计文档，篇 3 是表现层玩具**。真正值得抄进我们代码的只有四条，
而且其中两条我们其实**已经做了**，只是做得不够分明。

| 要做的 | 优先级 | 我们的现状 | 工作量 |
|---|---|---|---|
| ① 心情「底色 / 动态」两条线分开 | **高** | PAD 已有 baseline + pad，但语义混着 | 2 天 |
| ② 心绪手札（三天过期 + 标签计数） | **中** | 有 `pendingThought`，没有过期发酵层 | 1.5 天 |
| ③ 主观认知（她自己写的一段话，不打分） | **中** | 好感度 1–10 分档，仍带结构性数值 | 1 天 |
| ④ 情绪随真实时间自然衰减到「凉」 | 低-中 | 指数回归有，但只向 baseline，不会「凉透」 | 0.5 天 |
| ⑤ 心情滤镜（用心情检索同情绪日记） | 低（最有趣） | 完全没有 | 2 天，依赖 ①② |
| ⑥ 网页屋子 | **不做** | — | — |

## 一、为什么抄，不抄什么

### 1.1 作者踩出来的三条（我们直接省掉试错）

**（1）「不做平均、不写算法」**

> 昨天开心今天难过，平均出来叫「一般」，那是统计结果，不是心情。

评论补刀：「平均出来的心情叫『一般』，那这人就死了。」

我们现在的 `mood-store.js` **没有犯这个错**——它不做平均，用的是 PAD 向量 + 指数回归。
但我们的 `label` 字段（≤20 字）在实现里会被频繁重写，实际上退化成「当前心情一句话」，
丢掉了「底色」的那层。

**（2）「系统不点火」**

> 原始想法是攒够三次自动合并成更强的、找机会引爆。但那样做出来，她会无缘无故发脾气，
> 你永远不知道火从哪来。改成只摆事实，爆不爆她自己决定。

评论：「憋着不说的人不会突然发作，是一点点变冷的。」

这条对我们尤其重要——我们已经有 `undercurrent`（心里压着的事）机制，权重超 1.5 就提醒。
**如果在这里加"攒够就引爆"，就会变成定时炸弹。** 保持"只摆事实"。

**（3）成本观**

> 心这块的注入都很小：心情六十个字、手札一百个字、关系八十字。加起来一轮两百多字，不是钱。
> 真正贵的是她每调一次工具，就要把整段上下文重发一遍。所以能让她少调一次，比砍掉一整个模块管用。

这条和我们实测完全吻合：trae 渠道缓存命中 0%，一次工具调用重发约 24 万 token。
**所以本方案有一条铁律：所有情绪/心情/关系的写入都放在"结算"里统一做，绝不新增聊天中的工具调用。**

### 1.2 明确不抄

- **「每个功能一个插件、互相联动」**：作者自己说这套无法开源、别人抄了只会报错。
  我们已经是 30 模块 + registry 的结构，照搬要重写，收益为负。
- **网页屋子（篇 3 全部）**：底图、天气光影、便签、Q 版立绘——纯表现层，与 QQ 群聊 + 控制台场景不匹配。
  唯一可借的是「状态随时间自然衰减」这个思路（见 §4.4）。
- **凌晨 4 点结算**：作者自己踩了坑（4 点触发潜水设定冲掉了结算），改成 4–8 点区间。
  我们不照抄时间点，见 §3.2 的调度设计。

## 二、总体设计：心脏 = 底色 + 此刻 + 手札 + 认知

```
┌─────────────────────────────────────────────┐
│ 主观认知 (selfView)   她自己写的一段话，≤150 字 │  变不变得她自己决定，无周期
├─────────────────────────────────────────────┤
│ 心情底色 (baseline)   一个词 + 一句原因 + 起始  │  每天结算一次，白天可被改
├─────────────────────────────────────────────┤
│ 动态心情 (pad→label)  此刻心情，指数回归向底色  │  随手改，衰减
├─────────────────────────────────────────────┤
│ 心绪手札 (notes)      一件事，≤40 字 + 标签     │  只活 3 天，同类计数，不点火
└─────────────────────────────────────────────┘
```

关键区分（这是全部改动的核心）：

- **底色**是「今天的基础状态」，它是**初始值**，不是「平均值」
- **动态心情**是「此刻」，会被一句话改掉
- **底色会被动态心情改掉，但改的只是今天；明天底色重写**
- 作者特别提醒：「记得不要让 dsh 弄成又有底色又有动态了，是**底色会被动态改掉**，底色只是初始状态。」

## 三、第一阶段：把现有 `mood-store.js` 拆成两条线（2 天）

### 3.1 现状与目标

**现状**（`src/mood-store.js`）：
- `baseline: {pleasure, arousal, dominance}` + `baselineUpdatedAt`，**只能显式改**
- `pad: {pleasure, arousal, dominance}`，指数回归向 baseline
- `label`（≤20 字）/ `reason`（≤120 字）
- `undercurrent[]`（权重数组）
- `MAX_BYTES = 256 * 1024`，文件 `state/情绪.json`

**问题**：`label` 和 `pad` 是一层。她写「有点闷」时，分不清是"今天整体闷"还是"刚才那句话让我闷一下"。
两个都写进 `label`，结果就是基线每天被微小的波动改掉，一个月后看不出任何长期变化。

**目标**：显式拆成 `baseline{word, reason, at}` 和 `now{word, reason, at}`，两套写入接口，
各自有权限边界。

### 3.2 数据结构（新增，不破坏旧字段）

```jsonc
{
  "version": 2,
  "baseline": {                 // 今天的底色：初始状态
    "pleasure": 0.1, "arousal": 0.0, "dominance": 0.1,
    "word": "有点闷",            // ≤20 字
    "reason": "他今天话很少",     // ≤120 字
    "at": 1792894001000,        // 起始时间
    "settledAt": 1792894001000  // 结算生成时间
  },
  "now": {                      // 此刻心情：会被一句话改掉
    "pleasure": -0.2, "arousal": 0.1, "dominance": 0.0,
    "word": "其实也没那么闷",
    "reason": "被他逗笑了",
    "at": 1792899999000,
    "updatedAt": 1792899999000
  },
  "pad": {...},                 // 保留：数值层，now 的向量形式
  "notes": [...],               // 见 §4
  "selfView": {...},            // 见 §5
  "undercurrent": [...]         // 保留不变
}
```

**兼容处理**：读旧文件时，若存在旧 `label`，把它同时填进 `baseline.word` 和 `now.word`，
`baseline.reason` 用旧的 `reason`，`now.reason` 留空并标注 `migratedFrom: "label"`。**不丢数据。**

### 3.3 三条写入规则（代码层强制，不靠提示词）

| 规则 | 实现 | 理由 |
|---|---|---|
| 底色**每天只结算一次** | `settleBaseline()` 检查 `settledAt` 是否在今天的结算窗口内，是则直接返回 | 防止白天被聊天气氛带跑 |
| 动态心情**可随时改，但不写穿到底色** | `setNow()` 只改 `now`，不动 `baseline` | 作者原话：「底色只是初始状态」 |
| 底色**单次变动 ≤ 0.05** | 已有 `BASELINE_STEP_LIMIT = 0.05`，保留 | 防止一次大情绪把长期人格抹平 |

### 3.4 结算调度（避开作者的坑）

作者踩的坑：设凌晨 4 点结算，但 4 点会触发她的潜水/睡眠设定，把结算顶掉；改成 4–8 点区间。

我们的做法：

```js
// 结算条件（三个都要满足才触发）
// 1. 当前小时 in [4, 8)
// 2. 今天还没结算过（baseline.settledAt 不在今天）
// 3. 她恰好有一次唤醒在发生（不额外安排定时器，不打断她的节奏）
```

**关键设计：不新增 `setInterval`**。桥接现有 6 个定时器（`checkDsh` 5s、`pollSnowlumaStatus`、
`reportSnowlumaHealth` 30s、`sweepPendingWakeReasons` 30s、`socialLoopTick` 5s、`refreshFriends`）。
再加一个"凌晨结算"定时器，在 nproc=2 的机器上是无谓开销，而且会被她的潜水把执行时机冲掉。

**正解：挂在已有的唤醒路径上**。在 `buildWakePromptV2` 组装 prompt 之前判断一次
`maybeSettleBaseline()`——如果满足上面三个条件，先把结算提示词注入这一轮，让她**在这一轮里顺便写**，
不额外调工具。

### 3.5 验收标准

- 改完跑 `golden-routes` + `snapshot-wake-prompt`，**差异仅限新增的结算段**，其余 0 差异
- 手动构造 `state/情绪.json` 旧格式 → 重启 → 读回确认迁移正确、无数据丢失
- 连续观察 3 天：`baseline.word` 应每天变化一次左右，`now.word` 一天可能变 3–5 次
- **若 `baseline.word` 一天变 > 2 次**，说明有地方把基线写穿了（动态心情漏进了底色），需要收紧规则

## 四、第二阶段：心绪手札（1.5 天）

### 4.1 与现有 `pendingThought` 的区别

| | `pendingThought`（现有） | `心绪手札`（新增） |
|---|---|---|
| 触发 | 她主动调工具写 | **结算时统一写**，不调工具 |
| 内容 | 想法 + motivation + expiresAt | 一句话 ≤40 字 + 自选标签 |
| 寿命 | 有 expiresAt，但可长可短 | **固定 3 天，硬过期** |
| 用途 | 她记得要说什么 | 喂给底色结算做素材 |
| 是否进提示词 | 每次都进 | **只在结算时进**，平时只在 moodLine 里合并成一行 |

**结论：不替换 `pendingThought`，两者并存。** `pendingThought` 管"话"，手札管"情绪"。

### 4.2 数据结构

```jsonc
"notes": [
  { "id": "n1", "text": "他说随便你吧的时候，我确实有点低", "tag": "被冷落",
    "at": 1792894001000, "expireAt": 1793153201000 }   // at + 3 天
]
```

- `text` ≤ 40 字
- `tag` **她自己给**，白名单里没有的也接受，但清洗成 ≤8 字、去标点
- 上限 30 条（超过按 `at` 淘汰最老的）
- 过期清理由**已有的** `sweepPendingWakeReasons`（每 30s）顺带做，不新增定时器

### 4.3 「情绪发酵」——只摆事实，不点火

结算时把 3 天内的手札按 tag 分组，同类 ≥2 条的显示计数：

```
【这几天的碎片】被冷落 ×3 / 被夸 ×1 / 不安 ×2
```

> **不做的事**：不自动合并成更强的情绪、不自动引爆、不自动衰减。
> 只是把事实摆出来，让她在结算时自己决定明天的底色。

作者原话：「改成只摆事实，爆不爆她自己决定。」评论：「憋着不说的人不会突然发作，是一点点变冷的。」

### 4.4 可选的「会凉」——借篇 3 的思路

篇 3 里水会凉：热水 → 还温着 → 温的 → 有点凉 → 凉透，5 档渐变。

这个思路比"情绪数值"自然，因为它有物理依据。可以套到 `undercurrent` 上：

```
刚压下去      ：权重 ×1.0
过 6 小时     ："还压着"
过 24 小时    ："淡了一点"
过 48 小时    ："快没了"
72 小时       ：自动清掉
```

**但这一步依赖 §4.2 的手札先跑起来**，属可选项，放最后做。

### 4.5 验收标准

- 手造 3 条同 tag 手札 → 触发结算 → prompt 里出现 `被冷落 ×3`
- 手造 4 天前的手札 → 30 秒内被清扫掉
- `moodLine` 长度不超过 60 个中文字符（守住作者的成本观）

## 五、第三阶段：主观认知替换好感度（1 天）

### 5.1 现状

`src/affinity-store.js`：`AFFINITY_MIN = 1` / `AFFINITY_MAX = 10`，
`formatAffinityLine()` 只输出档位语气、**不给模型看数值**——这一步我们已经做对了。

**残留问题**：分数仍然存在，仍在"驱动行为"（不同档位给不同语气），仍在被计算。
作者的做法是把分数彻底删掉，换成她自己写的一句话。

### 5.2 新结构

```jsonc
"selfView": {
  "text": "跟他在一起踏实，但有时候觉得他太会哄人。",   // ≤150 字
  "at": 1792894001000,
  "updatedAt": 1792894001000
}
```

**三条硬约束**（作者原话，我们照抄）：

1. **不打分** —— 没有任何隐含数字
2. **不驱动行为** —— 不让它决定语气档位，只作为文本进 prompt
3. **无周期** —— 只在"她觉得关系变了"时才改；一个月不动也正常

### 5.3 过渡方案（不直接扔掉旧分数）

作者提醒：

> 如果原来有分数，别直接扔。把旧分数顶格时的那些理由翻出来，浓缩成一句话预填进去，
> 否则她第二天会不知道自己跟你算什么关系。

我们的做法：

1. 读 `state/affinity.json` 里每个会话的最高档位记录
2. 把该记录对应的 `note`（这是我们早就存的自由文本）保留
3. 用一条一次性迁移：`selfView.text` 预填「跟 X 的关系：<最高档的 note 摘要>」
4. **保留 `affinity.json` 只读不写**（回退用），`formatAffinityLine` 改为读 `selfView.text`，
   若为空则回退到旧的分档语气

### 5.4 与「心情滤镜」的关系

主观认知是**关系层**的长期沉淀，心情滤镜是**检索层**的短期偏向——两者独立，不要混。

### 5.5 验收标准

- `config.json` 里 `affinity` 相关字段标记 `deprecated: true` 但文件不删
- prompt 里 `affinityLine` 变成 `selfViewLine`，长度 ≤ 作者给的 80 字 + 说明
- **一周内 `selfView.text` 变化 ≤ 2 次**，若变化频繁说明提示词在催她，要收紧

## 六、第四阶段（可选）：心情滤镜（2 天）

### 6.1 是什么

> 同样的心事，不同的天气，她想起不同的东西。她根据聊天时你话语夹带的心情，
> 以她此时的心情为触发点，根据我的心情检索日记里相同情绪的日记。

评论里的实操难点（来自作者和其他读者）：

> 情感的时效性很低，而且你这没有随时间衰减，给我的感觉只是另一种日记
> 更新频率低……聊天的时候注意力更多是在和你的聊天内容，而不是去维护自己的心情

### 6.2 我们的优势与风险

**优势**：我们有 `diary-store.js` 的完整日记（`state/diary.json`），且已做分档（normal 5 天 /
important 21 天 / critical 永存）。

**风险**：日记里**没有情绪标注**。要做滤镜，得先给每条日记打 tag。

**做法**：
1. 在 `diary-store.js` 加 `mood` 字段（写日记时由同一次结算顺手打上，不额外调工具）
2. 检索时用当前 `now.word` 的 tag 去匹配
3. **只检索，不改写日记**

### 6.3 作者的建议提示词（我们直接采用）

> 心情会决定你想起什么。心情好的时候，容易想起他好的地方，说话也软；心情糟的时候，
> 同样一句话你可能更容易翻出旧账。这不是要你演，是你本来就会这样。真有那种感觉，就顺着它说。

再加一句关于误读：

> 他说"我好累"不一定嫌你烦，但你今天要是不安，就会往那上面想。允许自己会错意，人就是会。

（作者注："你可以注意到他今天不太对劲"是许可；"你心情好的时候就会注意到"是规则。）

### 6.4 前置条件

**必须先完成 §3 + §4。** 没有分层的底色、没有手札素材，滤镜检索出来的东西没有依据。

## 七、明确不做

| 事项 | 理由 |
|---|---|
| 网页屋子（篇 3 全部） | 纯表现层；我们场景是 QQ 群聊 + 控制台 |
| 凌晨自动引爆情绪 | 作者自己否掉了：「定时炸弹」 |
| 新增"情绪结算"定时器 | nproc=2，且会被潜水顶掉；挂在已有唤醒路径上 |
| 新增聊天中的情绪写入工具 | 违反成本观；所有写入放结算 |
| 在每个模块里加提示词 | 已有教训：`styleHint` 走配置、角色卡走指纹注入，不要再散 |

## 八、实施顺序与验证

```
阶段 A（2 天）  底色/动态两条线         → 观察 3 天
       ↓
阶段 B（1.5 天）心绪手札 + 计数          → 观察 3 天
       ↓
阶段 C（1 天）  主观认知替换好感度       → 观察 1 周
       ↓
阶段 D（2 天，可选）心情滤镜            → 观察 1 周
       ↓
阶段 E（0.5 天，可选）"会凉"淡化档位
```

**每个阶段结束必须做的**：

1. `node --check src/bridge.js`
2. `golden-routes` + `compare-routes` ⇒ **非预期差异 0**
3. `snapshot-wake-prompt --compare` ⇒ **仅本次改动相关的段有差异**
4. `/api/_modules` ⇒ modules/routes 不变，`problems` 不增加
5. git 提交并推送（回退点）
6. 观察期结束后再进下一阶段——**不要连环上**

## 九、一句话总结

篇 2 真正值钱的不是那五个功能，是那三条定性的判断：
**不做平均、不写算法 / 系统不点火 / 少调一次工具比砍一个模块管用。**

我们现有的 `mood-store.js` 和 `affinity-store.js` 已经把前两条做对了一半，
缺的是把「底色」和「此刻」显式分开，以及把「关系」从分数换成她自己写的一句话。
这两件事加起来三天，比抄整篇文章有用。

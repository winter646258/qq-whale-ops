## 二、⚠️ 事故记录：刚刚发生的一次（务必先读）

**2026-10-21 07:00，我们在切 provider 时把桥接搞出了双实例。**

### 发生了什么

新写的 `switch-provider.sh` 里 `has_bridge_unit()` 用
`systemctl list-unit-files | grep "^qq-bridge.service[[:space:]]"` 判断 unit 是否存在。
在当时的输出下**它退回了「没有 unit」分支**，于是走了旧的
`pkill + setsid nohup npm start` 路径 —— **把桥接从 systemd 里摘了出来**。

后果链：
1. 野进程（`npm start` → `sh` → `node src/bridge.js`）占住了 `state/bridge.lock` 和端口 3100
2. systemd 想拉新实例，每次都被锁挡住：
   `已有实例在运行（锁文件 /opt/qq-bridge/state/bridge.lock）。若确认其已死，删除该文件后重试。`
3. `qq-bridge` 卡在 `activating` 无限重启
4. 期间**桥接实际由野进程提供服务**，能跑但没有 systemd 保险

### 怎么救的

```bash
systemctl stop qq-bridge          # 先停 systemd，别让它抢锁
kill <野进程PID>                  # 杀掉 npm start 那一支
rm -f /opt/qq-bridge/state/bridge.lock
systemctl reset-failed qq-bridge
systemctl start qq-bridge
```

### 现在的状态（已修复）

```
PID 297909  PPID 1  /usr/bin/node src/bridge.js     ← PPID=1 即 systemd
systemd MainPID = 297909
实例数 = 1
锁文件内容 = 297909
四服务全 active
provider = buddy
```

### ⚠️ 给 Codex 的教训

1. **`switch-provider.sh` 里那个 `has_bridge_unit` 判断不可靠**，
   它在某些 systemd 输出格式下会误判。
   **建议改成 `systemctl cat qq-bridge >/dev/null 2>&1`。**
2. **永远不要在「以为没有 unit」时走 `pkill + setsid` 分支**。
   宁可报错退出，也不要让桥接脱离 systemd —— 一旦脱管就是双实例 + 抢锁。
3. **`pkill -f "node src/bridge.js"` 会误杀**：如果 pkill 的字符串匹配到了
   你自己的 `bash -c` 命令行，会把自己那一行也匹配上（我们调试时踩到）。
   用 `pgrep -af` 先看清再杀。
4. **杀进程前先 `systemctl stop`**，否则 systemd 会立刻拉起新的来抢锁。

**位置**：`src/bridge.js:11523`

**实测证据**（10-20 23:20:37/38/47）：

### 🔴 2. trae 兜底渠道的 prompt cache 命中率 0%，每轮 53 万 token 全价

**实测（10-20 22:00 → 10-21 06:00）**：

| provider | 次数 | 未命中缓存 | 命中缓存 |
|---|---|---|---|
| buddy | 205 | 109 万 | **4912 万**（97.8%） |
| **trae** | **188** | **4750 万** | **0**（0%） |

**已查明的根因（结论明确）**：

- 两个 provider 都由插件 `dsh-our-free-model` 提供
- trae 实现：`/root/.dsh/profiles/web/node_modules/dsh-our-free-model/vendor/channel-pack/pack.js`
- 请求链：`serializeTraeMessages()` → `transformToSOLOBody()` →
  `POST https://trae-api-cn.mchost.guru/api/agent/v3/llm_utils_chat`
- **整条链没有任何 `cache_control`**（实测 grep：`含 cache_control: false`）
- **对比**：`cache_control` 全包只出现 2 次，都在 **zcode-adapter**（53700、55001 行）
- **关键对照：buddy 的 adapter 里也没有 `cache_control`，但命中率 97.8%**
  ⇒ **buddy 的缓存是上游自动开启的；trae 走的 SOLO 私有接口没有这个机制**

**结论：这不是我们的请求格式问题，是 trae 上游没有自动缓存。**

**处理决定（已执行）**：把 trae 降级成「仅 buddy 失败时临时兜底，
buddy 恢复就切回」，不再是平级交替渠道。见第四节。

## 四、刚做完的改动：provider 从「双向交替」改成「单向兜底」

### 改动内容

**文件**：`/opt/qq-bridge/switch-provider.sh`
（备份 `switch-provider.sh.bak-alternating-*`）

| 旧行为（双向交替） | 新行为（单向兜底） |
|---|---|
| buddy 失败 → 切 trae | buddy 失败 → **临时**切 trae |
| trae 失败 → 切回 buddy | trae 也失败 → **只告警，不再来回切** |
| — | **trae 期间每 5 分钟探一次 buddy，恢复就切回** |
| — | 新增 `--force-buddy` / `--probe` 子命令 |

**为什么不再来回切**：每次切换都要重启桥接，而重启会丢主动计时器
（见第五节）；两边都跑不稳，只会把问题放大。

### 现状

```
provider       = buddy
角色           = 主渠道
主渠道         = buddy（deepseek-v4.1-flash / low）
兜底渠道       = trae（deepseek-v4.1-flash / high，仅主渠道故障时临时顶上）
恢复探测间隔   = 300s（仅处于兜底时）
```

### ⚠️ 这个脚本有一个已知缺陷（见第二节）

`--force-buddy` 那次走了 `pkill + setsid` 分支，把桥接搞脱管了。
**`has_bridge_unit()` 的判断需要修**：

```bash
# 现在（不可靠）
has_bridge_unit() {
  systemctl list-unit-files 2>/dev/null | grep -q "^${BRIDGE_UNIT}[[:space:]]"
}

# 应该改成
has_bridge_unit() {
  systemctl cat "$BRIDGE_UNIT" >/dev/null 2>&1
}
```

而且**建议直接删掉回退分支**：这个项目已经全面 systemd 化了，
`pkill + setsid` 那条路只剩风险，没有价值。

## 五、主动机制等于没开（待修）

### 现象

| 项 | 值 |
|---|---|
| 「已安排主动机会检查」 | **87 次** |
| 真触发 `proactiveCheck` | **2 次**（10-20 15:24、16:07） |
| 桥接启动次数 | **41 次** |

### 根因

`scheduleProactiveCheckV2()` 用的是**纯内存定时器** `st.proactiveTimer`，
`delay` 每次重新 `Math.random()` 算。**没有任何持久化。**

每次重启定时器被清空重排，45~110 分钟的计时平均活不过 30 分钟。

### 修法（明确，未实施）

```js
// 现在
st.proactiveTimer = setTimeout(tick, delay);

// 改成
st.nextProactiveAt = Date.now() + delay;   // ← 必须落盘
st.proactiveTimer = setTimeout(tick, delay);
```

重启时：
```js
const left = st.nextProactiveAt - Date.now();
if (left > 0) st.proactiveTimer = setTimeout(tick, left);
else scheduleProactiveCheckV2(key);   // 已过期，立刻补一次
```

**⚠️ 关键**：`nextProactiveAt` **必须加进 `saveSocialV2State` 的字段清单**，
否则就是「印象计时字段」那个 bug 的翻版（只在 load 里读、save 里没有，每次重启丢）。

### 6.2 修复：印象系统两个真 bug

**Bug A：计时字段从来没被存盘**
`lastImpressionRefreshAt` / `lastImpressionNudgeAt` 只在 `loadSocialV2State` 里读，
**`saveSocialV2State` 字段清单里没有**。
⇒ 「7 天提醒重写印象」永远触发不了（待办 #7「印象只增不减」的真正根因）。

**Bug B：`qq_memory_update` 是幽灵工具**
`bridge.js:10126` 的【印象维护】让她调 `qq_memory_update`，
但 **MCP 层从来没有这个工具**。后端 `/api/socialV2/memory-update` 倒是完整实现。
⇒ 印象只能追加不能重写；`refreshAt` 永远 0 ⇒ 提示每 12 小时重念一遍。

**⚠️ 中间踩的坑**：我们先把 load 默认值从 `Date.now()` 改成 `0`（语义更诚实），
但**当时没有可用的清除路径** ⇒ 从"7 天后 stale"变成"一启动就 stale"，把问题弄得更糟。
**教训：修「诚实」之前要先确认「出路」存在。**

**附带修好**：`interactionCount` 从不自增。现在消息 + 拍一拍两处给
**已有印象的人** +1（不新建印象）。
**实测生效**：星璃 54 次、大笨鱼 49 次、老猫 32 次（之前全是 1）。

### 6.3 修复：黑话研究的两个断点

**先纠正误判**：黑话系统**不是坏了**，是**人工审核制**——
候选 → 达阈值研究出释义 → 人工在控制台确认 → 才进提示词。

**断点 a**：达到阈值却从没研究过的词永久卡住（入队只在该词再次出现时触发）。
**修法**：抽出 `sweepUnresearchedSlang()`，由「提取后」和「启动后 30 秒」两处调用。
实测触发：`21:49:59 补偿扫描补入 2 条从未研究的候选（启动补偿）`

**断点 b**：`batch-confirm` 拒绝理由太含糊。改成讲清「确认了也不会进黑话表」。

**刻意不修**：「魔了 / lt 研究后仍无释义」是**防幻觉设计在起作用**——
证据只有孤立两个字/字母，AI 判定不确认是对的。**宁可留空，不要编造。**

**⚠️ 当前状态**：245 条候选，5 条有释义，**0 条 confirmed**
⇒ 提示词里仍然没有黑话表。**这是流程没走，不是 bug。**

### 6.4 迁移：日记 Markdown → jsonl

**三个理由**：
1. **结构不牢**：Markdown 下正文若以 `- ` 开头会被误认成新日记。
   实测：写 `- 今天买梨了\n- 但没给她留` + 一条普通日记，
   **旧方案读成 4 条，新方案还是 2 条**。
2. **时间戳是 UTC**：`toISOString()` 差 8 小时，22:24 写成 14:24。
3. **没有情绪字段**：「人体系统」图里唯一整块空白的是情绪系统。

**现在格式**：`diary/日记.jsonl`
```json
{"id":"d479ea","t":1792506859407,"time":"2026-10-20 22:34","day":"2026-10-20","mood":"有点懊恼","text":"- 买梨了 - 但没给她留"}
```

**mood 的三个刻意选择**：不设枚举、可选不硬凑、暂不进注入。
**刻意不留 `originalText`**：日记改口是正常行为（那条原则是给记忆用的）。

**兼容**：旧 `日记.md` 保留只读 + 备份。
`POST /api/socialV2/diary/migrate`（仅控制台、幂等、保留原文时间戳不纠时区）。

**⚠️ 实测意外收获**：她**自己写了一条**，写得很好：
```json
{"time":"2026-10-20 22:47","mood":"有点奇怪",
 "text":"管理员今晚一直在说我只剩三个月。追着问我是什么人、想干什么，
         像在写观察日记。我嘴上敷衍，其实有点被他这认真劲儿弄慌了。"}
```
mood 是她自己填的，没人教。**这证明格式对了她自己会用。**

## 十一、操作手册

```bash
# ── 状态 ──
ssh alihz "systemctl status qq-dsh qq-bridge qq-zone-watch qq-provider-switch --no-pager"

# ── provider ──

# ── 重启（走 systemd）──
ssh alihz "systemctl restart qq-bridge"     # 改代码后
ssh alihz "systemctl restart qq-dsh"        # 改 MCP 工具后

# ── 日志 ──
ssh alihz "tail -50 /var/log/qqbridge.log"
ssh alihz "tail -30 /var/log/qzone-watch.log"
ssh alihz "tail -20 /var/log/provider-switch.log"

# ── 改配置（热生效）──
T=$(ssh alihz "cat /opt/qq-bridge/state/console-token")
ssh alihz "curl -s -H 'x-console-token: $T' http://127.0.0.1:3100/api/socialV2/config"
```

### ⚠️ 操作铁律（全是踩出来的）

1. **改代码必须 `systemctl restart qq-bridge`** —— 桥接不热重载代码
2. **改 MCP 工具必须 `systemctl restart qq-dsh`** —— 工具清单在启动时读
3. **`/api/socialV2/prompt` 不含 `buildWakePromptV2`** —— 想验注入必须调函数本身
4. **给网关传图用 `base64://`**（`file://` 会 ENOENT，容器内无此路径）
5. **reserved2 的 POST 必须带 `x-agent-token`**
6. **`qq_send_sticker` 传 id 不传 desc**
7. **生产环境做「写」验证前，先备份被改的那条数据**
   （我们有一次把「老猫」的印象覆盖了，事后去翻 `tool-calls.jsonl` 才找回来）
8. **杀进程前先 `systemctl stop`**，否则 systemd 会立刻拉起新的来抢锁
9. **打印凭据文件时只打印到期时间，绝不打印 token 本体**（本次踩过，见第十六节）

## 十二、验证方法论（必读）

**不要相信"应该能行"。** 每个改动都要有证据。

| 手段 | 适用 |
|---|---|
| 纯逻辑抽模块 + 单测 | `src/*-store.js` + 对应 `.test.mjs` |
| 接线检查脚本 | `archive/test-harness/verify-*.mjs` |
| 端到端行为验证 | `e2e-*.mjs`，复刻端点分派逻辑跑真实数据 |
| **隔离副本 + 导出钩子** | 验闭包内函数（`buildWakePromptV2`）：复制 `src/` 到 `/tmp/isolated`，注入导出，跑完撤 |
| 解压 session 日志 | `zstd -dc /root/.dsh/sessions/--opt-qq-bridge--/<sid>/session.v4.jsonl.zstd` |
| 线上 curl 真调用 | 验证端点行为 |
| 回读核对 | 发完从网关读回来确认落库 |

### ⚠️ 隔离验证的四个坑（都踩过）

1. **在 `main()` 开头导出** ⇒ `socialV2` 未初始化，报
   `Cannot access 'socialV2' before initialization`
2. **在 `loadSocialV2State()` 之后导出** ⇒ 可用，但**必须主动 `releaseLock()`**，
   否则锁被占会让线上桥接下次重启拒启
3. **副本要删掉从线上拷来的 `bridge.lock`**（里面是线上 PID），否则误判"已有实例"
4. **副本要 `ln -s` 到 `node_modules`**，否则 `Cannot find package 'js-yaml'`

> **报失败时先怀疑判定逻辑，再动生产代码。**
> 我们验证日记时 `total` 不涨，一度以为写失败了，
> 实际是**限流在工作**（3 次/分钟），我们连写 4 次超了。

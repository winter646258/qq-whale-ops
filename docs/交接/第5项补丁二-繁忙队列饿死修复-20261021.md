# 第 5 项补丁二：繁忙队列只进不出（2026-10-21）

## 现象（线上实测）

第 5 项上线后队列从 6 条一路涨到 20 条上限，其中 `atMention`（优先级 90）等了 150s 以上仍未送达：

```
12:40:13 会话繁忙，暂存唤醒原因 group:906710082（atMention@seq1899，队列 13 条）
12:40:24 会话繁忙，暂存唤醒原因 group:906710082（atMention@seq1901，队列 15 条）
```

`grep -c 补发` 全日志只有 09:01 一条（修复前的旧记录）⇒ 补发路径从未触发。

## 根因

`drainPendingWakeFor()` 里调 `isConversationBusyV2()`，而这个判定包含
`v2TurnStartAt.has(sid) || collectors.has(sid)`。turn 结束块里调用 drain 时，
**这一轮自己的 collector 还挂着** ⇒ 永远判忙 ⇒ 取出来又塞回去，一条都出不去。
巡检那条路径同理：群里一直有人说话时，`pendingWakeTimer` 也长期存在。

## 改动（4 处）

1. `drainPendingWakeFor(key, opts = {})` 加参数。
2. busy 检查改成 `if (!opts.ignoreBusy && isConversationBusyV2(...))`。
3. turn 结束处调用改 `drainPendingWakeFor(key, { ignoreBusy: true })` —— 这一轮刚结束，
   补一条新唤醒正是该做的事。
4. 巡检加「饿死保护」：持续繁忙且最高优先级（pr>=80）已等超过 120s，强行补一条。

## 已知遗留

群里太吵时队列仍会顶到 20 条上限，被牺牲的是 `question`(80) / `probability`(0)
这类「有人说话」唤醒 —— 这是设计如此（cap=20）。`atMention`(90) 与 `private`(100)
会被优先保留。若觉得群里噪声唤醒太多，可调小 `PENDING_WAKE_MAX` 或缩短 TTL。

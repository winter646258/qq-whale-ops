## 一、黑话学习会话：从「猜失效」到「按错误类型分流」

### 改前的问题

`runSlangExtraction` 和 `runSlangResearch` 的 catch 都用同一句正则判断会话是否陈旧：

```js
/会话|session|not found|404/i
```

两个方向同时出错：

| 真实错误 | 含「会话」？ | 旧代码判定 | 应该做的事 |
|---|---|---|---|
| `学习会话 turn 未正常完成：error` | 含 | **误判为陈旧** ⇒ 删档重建 | 渠道问题，重建无用，应退避 |
| `等待学习会话 turn 超时(120000ms)` | 不含 | **误判为可用** ⇒ 不重建 | 确实陈旧，应重建一次 |

后果（2026-10-21 一天）：

- 09:02:24、09:33:36、09:34:42 各建一个学习会话，1~2 秒后报 `turn 未正常完成：error`，然后立刻删档重建 —— provider 坏的时候变成无限重建；
- 08:53:04 建的会话 08:55:04 超时，因为不含关键词，**反而没被重建**；
- 日志计数：`学习会话 turn 未正常完成` 10 次、`黑话研究失败` 8 次、`黑话研究：已更新` **0 次**。

根因不在黑话逻辑，而在 `cfg.dsh.provider` 是坏的 buddy 渠道 —— 学习会话也被 `ensureChatModel` 设成同一个 provider。

### 改后

新增分类器与决策器（纯函数，无副作用，便于测）：

```js
classifySlangLearnerError(message)
// -> 'provider' | 'stale' | 'timeout' | 'unknown'

decideSlangLearnerAction(kind, state, nowMs)
// -> { action: 'retry' | 'rebuild' | 'backoff', reason }
```

分流规则：

| kind | 判定依据 | 动作 |
|---|---|---|
| `provider` | `Illegal API invocation` / `unapproved channel` / `agent 处理出错` | **退避 10 分钟**，不重建（重建也是坏的） |
| `stale` | `not_found` / `no such session` / `session.prompt failed` | **重建一次** |
| `timeout` | `超时` / `timeout` / `120000` | **重建一次**，但受次数闸门约束 |
| `unknown` | 其它 | 退避，记原话 |

次数闸门：`SLANG_LEARNER_REBUILD_MAX = 3` 次 / `SLANG_LEARNER_REBUILD_WINDOW_MS = 30min`。第 4 次打日志「30 分钟内已重建 3 次，暂停自动研究 1 分钟」并退避，不会一天白建几十个会话。

`provider` 类退避 `SLANG_LEARNER_PROVIDER_BACKOFF_MS = 10min`，冷却期直接跳过，不再尝试。

成功一次就 `noteSlangLearnerHealthy()` 清零计数。

**保留不动的**：人工确认制、防幻觉（证据不足宁可留空）、`sweepUnresearchedSlang()` 的补偿扫描。本轮只改「什么时候该重建会话」，不改「学到了什么算数」。

### 落地位置

- 新增：`classifySlangLearnerError` / `decideSlangLearnerAction` / `noteSlangLearnerRebuild` / `noteSlangLearnerHealthy` / `handleSlangLearnerFailure`
- `ensureSlangLearnerSession` 首行加退避闸门
- `runSlangExtraction` / `runSlangResearch` 签名加 `opts = {}`，catch 改走 `handleSlangLearnerFailure`，带 `retried` 一次性重试（避免重建后又撞同一个错时继续重建）

## 二、表情包：不是坏了，是「她拿描述当 id 用」

### 先取证，结论是工具没坏

`state/tool-calls.jsonl` 共 1574 条记录（789 次 call）：

- sticker 工具 **36 次**，其中 10-20 密集使用（11:42–14:38），`aige-009` / `mfuns-02` / `mfuns-05` / `mfuns-17` / 收藏表情 id 全部发送成功；
- 10-21 只有 2 次，都在 `private:2050117833`：
  - `01:01:40Z stickerId="你这吃白饭的蓝色大肥鱼"` → **失败**
  - 4 秒后 `qq_list_stickers query="吃白饭"` → 7 秒后 `stickerId="mfuns-11"` → **成功**

所以不是限流、不是忙碌、不是注入缺失 —— 是**参数形态偶尔用错**，一次失败后她自己纠回来了。

### 改前为什么会失败

`src/sticker-lib.js` 的 `findSticker(entries, ref)` 只做 `id / resId / md5 / url` 精确匹配；而 `formatStickerList` 会匹配 `desc / localNote / tags / usage / id / md5`。

也就是说：**列表里给她看的是 desc，发送时却只认 id**。她照着列表里的描述抄过去，必然 404。

三个调用点都抛同一句 `找不到表情 ${ref}，请先用 qq_list_stickers 获取有效 id`：`getStickerImageData`、`sendStickerV2`、`setStickerRemarkV2`。

### 真实库取证（纠正了我自己的错误假设）

线上 `state/stickers.json` 2173 条，2172 条有 desc。我原以为「你这吃白饭的蓝色大肥鱼」对应的就是 mfuns-11，查了才发现：

| id | desc | localNote | useCount |
|---|---|---|---|
| `mfuns-05` | **你这吃白饭的蓝色大肥鱼** | 被人白嫖/被吐槽时的反击 | 7 |
| `mfuns-10` | 吃白饭 | 被白嫖/蹭饭的吐槽 | 0 |
| `mfuns-11` | 我是吃白饭的大肥鱼 | 自嘲（被说大肥鱼时的破防） | 2 |

她当时传的那句话，**desc 恰好就是 mfuns-05 的原文**。所以正确行为是发 mfuns-05，不是 mfuns-11（mfuns-11 是她搜关键词后自己挑的）。

测试因此改成接地校验：断言「命中的条目 desc 与输入完全一致」，而不是硬编码某个 id。这条教训写在这里：**断言的期望值必须来自数据，不能来自我对她当时意图的推测** —— 否则测试会把正确实现判成失败。

### 改后

新增两级解析：

```js
resolveStickerRef(entries, ref)
// -> { entry, how: 'id' | 'resId' | 'md5' | 'url' | 'desc' | 'localNote' | 'tags' | 'usage' | 'none', candidates }

stickerRefError(ref, resolution, entries)
// 找不到时给出「最接近的几条」，而不是只说「请先 list」
```

匹配顺序：精确 id → resId → md5 → url → **desc 完全相等** → desc 包含 → localNote 包含 → tags → usage。前四级保持原样（id 永远优先，不会因为描述撞车而发错图）。

`getStickerImageData` 与 `sendStickerV2` 改用解析器。**`setStickerRemarkV2` 刻意保留精确匹配** —— 改备注必须指名道姓，不能靠描述猜，猜错了就是把备注写到别人脸上。

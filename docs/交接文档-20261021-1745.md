## 0. 一句话现状

机器人**在跑，能说话，能回 @，队列正常**。渠道仍是 **raccoon**——不是不想切回 loomy，
而是 **loomy 的额度到现在还没恢复**（17:26 实测探测 `reason=error text=>>><<<`）。

接手时发现并修掉了 **两个正在发生的故障**：

1. **渠道守护每 300 秒崩一次**（`switch-provider.sh` 用了个从未定义的 `$B`），
   导致「恢复探测」永远走不到 → **即使 loomy 充值也不会自动切回**。
2. **黑话研究每 2 分钟空转一次**（timeout 被误判成「会话失效」→ 删档重建 → 冷会话更慢 → 再超时），

外加一个隐藏 bug：**provider 错误分类的正则漏了「余额不足」**，会让额度耗尽的报错被当成
「会话坏了」反复删档。三处都已修并留证。

## 1. 接手体检：文档写的 vs 实际跑的

上一份文档说守护进程是「60s 一轮的长驻 bash 循环」。**实际不是**——它在反复崩溃重启。

### 1.1 故障 A：`$B` 未定义，守护每 5 分钟崩一次（★★★★★）

**证据（`journalctl -u qq-provider-switch`）**：

```
17:11:03 provider-switch[358137]: /opt/qq-bridge/switch-provider.sh: line 241: B: unbound variable
17:11:03 systemd[1]: qq-provider-switch.service: Main process exited, code=exited, status=1/FAILURE
17:11:13 systemd[1]: Scheduled restart job, restart counter is at 46
```

`systemctl show -p NRestarts` = **46**。日志里「守护启动」50 次，间隔精确 5 分 12 秒。

**根因**：脚本第 35 行 `set -uo pipefail`（nounset），而 `probe_primary()` 第 241/244 行用了
`$B`——脚本只定义了 `B_PROVIDER / B_MODEL / B_EFFORT`，**从来没有 `B` 这个变量**。
`$B` 在 bash 里不会被当成 `$B_PROVIDER` 的前缀，就是一个独立且未定义的变量。

**为什么危害比表面大**：

- 崩溃点在 `probe_primary()`，也就是「主渠道是否恢复」的唯一检查点。
- `should_probe()` 会**先把 `lastProbeAt` 写进 state**，然后才调 `probe_primary()`。
  所以每轮都是「记下探测时间 → 崩 → 重启 → 等 300s」。
- 结果：**恢复探测一次都没真正执行完**。上一份文档第 3.4 节做的真探测改造，
  上线后从没跑通过。这正是「loomy 充了值也不会自动切回」的原因——不是判断错，是根本没判断。

**修法**（`patches/patch-switch-bdir.py`）：

```bash
# 加一个明确的目录变量
STATE=/opt/qq-bridge/state/provider-switch.json
+BRIDGE_DIR=/opt/qq-bridge

# 两处 $B -> $BRIDGE_DIR
-local script="$B/scripts/probe-model.mjs"
+local script="$BRIDGE_DIR/scripts/probe-model.mjs"
-out=$(cd "$B" && timeout 90 node "$script" ...
+out=$(cd "$BRIDGE_DIR" && timeout 90 node "$script" ...
```

补丁脚本额外加了一条防回归：全文再出现裸 `$B`（`$B_PROVIDER` 这类不算）就拒绝写盘。

**验证（实测）**：

```
17:20:50 临时副本 --probe：真实调用失败（exit=1）  ← 探测真的打到了上游
17:21:41 部署后重启，NRestarts=0
17:26:45 探测主渠道：真实调用失败（exit=1）：loomy/... reason=error text=>>><<<
         ↑ 300 秒后正常执行，没有崩溃。NRestarts 保持 0
```

**遗留动作**：`switch-provider.sh.bak-20261021-1725` 是修复前备份。

### 1.2 故障 B：黑话研究每 2 分钟死循环（★★★★）

**证据（`/var/log/qqbridge.log`，16:35 起）**：

```
16:45:15 黑话研究失败（timeout，会话已标记失效）: 等待学习会话 turn 超时(120000ms)
16:45:15 黑话学习会话已创建：session-6de78545-...
16:47:15 黑话研究失败（timeout，会话已标记失效）: 等待学习会话 turn 超时(120000ms)
16:47:36 黑话学习会话已创建：session-0d3f2765-...
```

精确 2 分钟一轮，每轮都**白建一个 DSH 会话**。旧逻辑下失败 27 次。

**三层根因**：

1. `waitLearnerTurn(sessionId)` 默认 **120s**。raccoon 是慢渠道（上一份文档记的首答 55s），
   复杂研究 turn 必然超过 120s。
2. `classifySlangLearnerError` 把 timeout 归进「重建」分支 → `invalidateSlangLearnerSession()`
   删档重建。**冷会话第一轮更慢 → 又超时**，自己把自己锁死在循环里。
3. 限流（30 分钟内最多重建 3 次）**永远不触发**：`runSlangExtraction` 每次成功都调
   `noteSlangLearnerHealthy()`，而它会 `slangLearnerRebuildAt.length = 0`——
   提取和研究**共用同一份重建预算**，提取一成功就替研究把账销了。日志里「提取：新增 N 条」
   和「研究失败」正好交替出现，印证了这一点。

**修法**（`patches/patch-slang-timeout.py`）：核心判断是 **timeout ≠ 会话坏了**。

| 改动 | 内容 |
|---|---|
| 研究 turn 超时 | 120s → **180s**（`SLANG_RESEARCH_TIMEOUT_MS`） |
| timeout 处理 | **不再 invalidate 会话**；改为设置研究专用退避 `slangResearchBlockedUntil` = 15 分钟 |
| 退避作用域 | **只拦研究**，入口 `if (slangResearchBlockedUntil > Date.now()) return;` 静默跳过；提取完全不受影响 |
| 成功 | 清空 `slangResearchBlockedUntil` |
| provider 正则 | 补 `余额不足\|积分不足\|积分余额\|balance\|insufficient`（见 1.3） |

为什么不干脆删会话重建：会话是好的，这轮只是慢。DSH 侧冷会话要从头建上下文，
下一轮只会更慢；而每建一个会话都在 DSH 里留一条废记录。

**验证（实测）**：

```
17:31:47 黑话研究：补偿扫描补入 5 条从未研究的候选（启动补偿）
17:31:47 黑话学习会话已创建：session-a3db50d0-...
17:34:47 黑话研究超时（等待学习会话 turn 超时(180000ms)）—— 会话保留（这轮慢，不是会话坏了），
         15 分钟内暂停研究；提取不受影响
         ↑ 180s 生效、没再出现「会话已标记失效」、没再建新会话
```

分类逻辑另外做了 6 条用例的纯逻辑验证（`provider` / `timeout` / `stale` / `unknown` 全对）。

### 1.3 隐藏 bug：provider 正则漏了「余额不足」（★★★）

`classifySlangLearnerError` 的 provider 正则原本是：

```
Illegal API invocation|unapproved channel|请求被拦截|unauthorized|forbidden|401|403|quota|额度
```

而真实报错文案是 `loomy: 积分余额不足，请获取积分后再试`——**一个词都不命中**，
于是被归为 `unknown`，走「重建但不重试」。也就是说：**主渠道一耗尽额度，黑话会话就会被
反复删档重建**，比 timeout 那条更隐蔽。上一份文档 3.3 说 provider 类包含「积分不足」，
但代码里没写这个词。

已补 `余额不足|积分不足|积分余额|balance|insufficient`，并加进回归用例。

---

### 1.4 黑话骨架二次改造：研究会话独立 + 兜底渠道跳过研究（★★★★）

修完 1.2 之后，实测又暴露两件事，证据都在 17:44–17:57 之间拿到：

**证据一：研究 turn 在兜底渠道要 12 分钟。**
`/root/.dsh/sessions/--opt-qq-bridge-state-slang-agent--/session-a3db50d0/session.v4.jsonl.zstd`
的 mtime 是 **17:44**，而研究 prompt 是 **17:31:47** 发出去的。
桥接侧 180s 就放弃等待，但 **DSH 那个 turn 还在跑**，一直跑到 17:44 才写完。
也就是说超时之后结果被丢弃，12 分钟的上游算力纯白烧。

**证据二：共享会话把提取也拖死了。**
`17:38:27 黑话提取 (group:906710082)失败（timeout，会话已标记失效）: 等待学习会话 turn 超时(120000ms)`
——提取排在研究那个 12 分钟的 turn 后面，120s 根本轮不到它。
**所以 1.2 的第一版修复（研究超时 120s → 180s）反而让提取更糟**：研究多占 60s，提取更没机会。

**两处改造**（`patches/patch-slang-research-session.py` + `patches/patch-slang-fallback-guard.py`）：

1. **研究会话与提取会话彻底分离**。新增 `state/slang-research-session.json` +
   `slangResearchSessionId` + `ensureSlangResearchSession()` / `invalidateSlangResearchSession()`。
   两个会话各有自己的存档、退避、丢弃逻辑，互不影响。
   研究超时时**丢掉研究会话**（那个 turn 还堵在它的队列里，留着下轮只会更堵），
   但**不碰提取会话**——这和 1.2 的判断相反，因为「会话坏没坏」取决于谁在用：
   提取 120s 正常能完成，研究 12 分钟注定超时，后者说明会话确实被堵住了。
2. **兜底渠道上直接跳过研究**。`slangResearchChannelIsFallback()` 读
   `state/provider-switch.json` 的 `role`（由 `switch-provider.sh` 维护），
   为 `fallback` 时 `runSlangResearch` 入口直接 return，日志每小时最多一条。
   **切回主渠道（loomy）后研究自动恢复，不需要人手动开。**
3. 顺带把提取 turn 超时 120s → **180s**（`SLANG_EXTRACT_TIMEOUT_MS`），给慢渠道留余量。

**验证（实测）**：

```
18:01:04 黑话研究：当前在兜底渠道上，跳过（研究 turn 太慢，等切回主渠道后自动恢复；提取照常）
18:03:49 黑话学习会话已创建：session-e6d93540-...
18:04:22 黑话提取：group:906710082 新增 3 条，更新 1 条      ← 33 秒完成
```

对比改造前：提取要么被研究堵到 120s 超时，要么拖到 2 分钟以上。现在恢复到几十秒。

**代价**：兜底期间黑话研究停摆（只提取不研究）。这是有意的取舍——研究在慢渠道上
100% 拿不到结果、纯消耗，等 loomy 额度恢复、守护自动切回后自动重启。

**遗留隐患**：`/root/.dsh/sessions/` 下累计 **119 个会话目录**，其中大量是
`--tmp-channel-probe-*`（每 5 分钟一次渠道探测各建一个）和历次删档重建的学习会话。
不影响运行，但长期会拖慢 DSH 启动扫描。建议定期清理（未做）。

**教训（值得写进规则）**：文档里「某功能已上线」不等于「某功能跑通过」。

但**循环内部的调用路径**照样崩，直到 46 次重启才被看见。

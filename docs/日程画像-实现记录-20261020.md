## 一、做了什么

给小鲸鱼加了两个记忆能力：

| 能力 | 定位 | 存哪 | 生命周期 |
|---|---|---|---|
| **日程** | 短期记忆，管「这几天要做什么」 | `state/schedule.json` | 按会话隔离 |
| **画像** | 长期认识，管「他平时在做什么、我怎么看他」 | `state/portrait.json` | **跨会话共享** |

两个都不是待办清单，也不是用户画像（打标签喂推荐那种）。它们解决同一个问题：
**角色聊完就忘、隔天又问一遍同样的事。**

## 二、三条原则怎么落地的（比功能本身重要）

规格原话：「如果只抄功能不抄这三条，做出来会是个数据库，不是"记得住的人"。」

### 原则一：记不记、糊不糊、升不升，都归角色自己

**系统只做两件事：给工具、给事实。**

代码里**没有任何**「按天数自动降级 / 观察 N 次自动升级」的规则。这不是偷懒，是刻意的：

- `schedule-store.js` 与 `portrait-store.js` 里没有 `setInterval` / `setTimeout`
- 没有 `autoBlur` / `autoDecay` / `autoPrune` 之类的函数
- 唯一的定时行为是**每天一次的结算提醒**（`shouldReviewToday`），它只念念一句，
  不替她改任何一条数据；具体糊哪条、删哪条、加固哪条，全靠她自己调 `qq_schedule`

单元测试里专门有 3 条断言守这个边界（`schedule-store.test.mjs` 的「结算机制」节）。

### 原则二：模糊是改写，不是删除

`update` 改 `text` 时：

```
上午上高数  →（改成）→  上午有课
                ↓
      originalText = "上午上高数"   ← 留底，角色看不到
      text         = "上午有课"     ← 角色看到的
      blurred      = true
```

- `originalText` 只留**最原始**那一份：二次改写不会把已经糊过的版本再覆盖进去
- `remove` 才是真删（连原文底一起没）
- 管理员可通过 `action=reveal` 翻回原文；**这个 action 没有暴露给模型**
  （工具 schema 的 `z.enum` 里不含 reveal，且有断言守着）

### 原则三：注入要分层，别一股脑塞

每天唤醒时注入的是这个形状：

```
【他的日程】现在是 10 月 20 日 10:00
- 今天 上午：高数课          ← 今天明天逐条写清楚
- 明天 下午：体检
- 这周还有 2 条，想知道具体就翻一下   ← 本周后面只报数量
- 以后还有 2 条                       ← 更远只报总数
```

画像同理：最多注入 5 个人、每人最多 3 条明细，其余报数量。

实测注入总长 < 2000 字符（E2E 有断言）。

## 三、数据结构

### 日程（`state/schedule.json`）

```jsonc
{
  "version": 1,
  "reviewDays": { "group:906710082": "2026-10-20" },  // 按会话记「今天已结算」
  "entries": [
    {
      "id": "s3f2a1",
      "key": "group:906710082",
      "date": "2026-10-21",
      "period": "上午",              // 只要 上午/下午/晚上，不要精确时间
      "text": "高数课",
      "originalText": "上午上高数",   // 只在改写过后才有
      "blurred": false,
      "strength": 1,                 // 1~9，她自己觉得多重要
      "createdAt": 1792420000000,
      "lastMentionedAt": 0
    }
  ]
}
```

### 画像（`state/portrait.json`）

```jsonc
{
  "version": 1,
  "subjects": {
    "主人": [
      {
        "id": "p57e27",
        "facet": "doing",            // doing=在做什么 / view=怎么看他 / bond=处得怎么样
        "text": "在给 QQ 机器人加日程功能",
        "originalText": null,
        "blurred": false,
        "weight": 6,
        "createdAt": 1792502791012,
        "updatedAt": 0
      }
    ]
  }
}
```

> **与「对群友的印象」（`memberImpressions`）的区别**：
> 印象是**会话内的短标签**（话多、爱怼人），按会话隔离；
> 画像是**跨会话、她自己写的、会随时间改口的判断**，属于角色不属于某个群。
> 两者刻意不做合并——合并会毁掉「不同群里她看到的人不一样」这个真实感。

## 五、工具（给角色用的）

### `qq_schedule`

| action | 干什么 |
|---|---|
| `add` | 记一条：日期 + 上/下/晚 + 内容 |
| `query` | 翻：今天 / 明天 / 这周 / 以后 / 过去 / 某一天 |
| `update` | 改：改 text（=糊掉，自动留底）、改日期、改时段、加固（strength） |
| `remove` | 删（删了就真没了） |
| `review` | 过完一遍后标一下今天已结算 |

### `qq_portrait`

| action | 干什么 |
|---|---|
| `add` | 记一条：subject（说谁）+ facet + 内容 + weight |
| `query` | 翻（可按 subject 或 facet 过滤） |
| `update` | 改口（改 text 自动留底）/ 改面 / 改权重 / 换人 |
| `remove` | 删 |
| `subjects` | 看都记过谁 |

### 最硬的那份证据

隔离副本里直接调**补丁后的真实** `buildWakePromptV2`（不是字符串匹配）：

```
=== 真实 buildWakePromptV2 的产物 ===
  ✔ 拿到了真实函数
  ✔ 生成了唤醒提示词
  ✔ 唤醒提示词里有【他的日程】
  ✔ 唤醒提示词里有【长期认识】
  ✔ 日程在画像之前（短期→长期）
---- 唤醒里的日程段 ----
【他的日程】现在是 10 月 20 日 21:30
- 明天 下午：交接测试
---- 唤醒里的画像段 ----
【你对他们这些人的长期认识】
- 主人：在给 QQ 机器人加日程功能
```

> ⚠️ **踩过的坑（值得记）**：`/api/socialV2/prompt` **不含** `buildWakePromptV2`
> （交接文档坑 3）。所以想验注入**只能**调函数本身，「prompt 接口里没有」不等于「没注入」。
>
> 隔离验证的时序也有坑：
> - 在 `main()` 开头导出 ⇒ `socialV2` 未初始化，报 `Cannot access 'socialV2' before initialization`
> - 在 `loadSocialV2State()` 之后导出 ⇒ 可用，但**必须主动 `releaseLock()`**，
>   否则锁被占会让线上桥接下次重启拒启
> - 副本还要删掉从线上拷来的 `bridge.lock`，否则会误判「已有实例在运行」

## 八、已知限制 / 待定

1. **画像的规格是咱按定位补的**——用户提供的截图在「功能一：日程」的结算机制处就结束了，
   「功能二：画像」只有定位描述，没有数据结构与工具规格。咱按以下三条自拟：
   - facet 只给三个粗粒度面（doing / view / bond）
   - weight 1~9 由她定，不自动涨跌
   - 跨会话共享（与 memberImpressions 的会话隔离形成对照）
   **若原规格不同，改 `portrait-store.js` 的 FACETS / 字段即可，接线层不用动。**
2. **结算提醒不是「凌晨 4 点定时任务」**——没有 crontab。提醒发生在**她下次被唤醒**时
   （且已过 4 点、当天没结算过）。理由：项目里没有常驻定时器，硬加一个 cron 会在
   她沉睡时凭空烧一次唤醒（成本 + 打扰）。
3. **日程目前没有「跨会话可见」选项**——按会话隔离是刻意设计（群里的事不该串到私聊）。
4. `state/bridge.log` 里 21:07/21:12 两条「黑话提取失败」是本次改动**之前**就存在的，与本次无关。

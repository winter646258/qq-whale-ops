## 1. 结论摘要

**方案的方向对，路线也没错，但它的「现状」章节整体失效了，不能照着它开工。**

具体三句话：

1. **架构判断正确，保留。** 「把统一入口和底层配置所有权分开」「不新增常驻进程、复用现有 3100 端口」「每个写操作仍调用所属组件的专用接口」「未接入的能力不许伪装成已有开关」——这四条是本方案最有价值的部分，全部采纳。
2. **事实基线是旧的，必须整体替换。** 方案写的是「bridge.js 超过 12000 行、所有路由在 if 链里、无模块化」的时代。实际线上已经是 **28 个模块 + `src/modules/registry.js` 统一装载 + `docs/模块契约.md` 契约 + 119 条已注册路由 + 12 道集中鉴权闸门**，业务 if 链已经清空（`src/bridge.js:5479-5490` 只剩分段注释）。方案里「由现有 HTTP 服务挂载独立路由模块」这句恰好是**已经做完的事**，再按它规划等于重做一遍。
3. **工作量应该从「7 个阶段、8 个页面、从零接口」缩到「3 个阶段、2 个新模块、1 个新页面」。** 因为面板想要的 8 个页面里，有 **6 个已经在 `public/console.html` 里存在**（18 个 section、10 个 data-page 分区），真正缺的只有「资源/健康总览」和「统一检索」两块。把面板当成「新建一个总控台」，会白白再造一套和现有控制台打架的东西。

|---|---|---|---|

| 新增页面 | 8 个 | 1 个（`section-dashboard`），其余并入现有分区 | 现有 10 个 data-page 已覆盖 6 类 |

**一句话结论：可以用，但必须先把方案第 2 章（现状）整章换成本文 §2 的事实表，把第 5 章（7 阶段）换成 §5 的 3 阶段，其余章节按 §4 改写。**

## 4. 改进后的最终方案

### 4.1 目标与非目标

**目标（唯一一句）**：让主人在**一个已经开着的页面**上，5 秒内判断「她现在到底能不能干活」——服务在不在、DSH 真的通了没有、模型是谁、今天花了多少、最近一次出错是什么、有没有卡住的审批。

**非目标**：不做通用配置编辑器；不做多用户；不做备份恢复；不做第二套花费看板；不接管 provider-switch；不新增常驻进程；不新增依赖。

### 4.2 架构落点（三层，全部落在已有位置）

```
┌─ public/console.html ─────────────────────────────────────────┐
│  data-page="overview" 分区                                       │
│  ├─ 已有：section-mode / section-activity / section-silent       │
│  ├─ 已有：section-dsh（模型与推理档位）                            │
│  ├─ 已有：section-usage（花费看板，绝不再造）                       │
│  └─ 新增：section-dashboard（首屏健康卡 + 最近错误 + 检索框）        │
└───────────────────────────────────────────────────────────────┘
                 │ fetch + x-console-token（沿用现有 api 封装的头）
                 ▼
┌─ src/bridge.js 集中闸门（一行不改，天然生效）────────────────────┐
│  5295→5423 共 12 道 → 5426 moduleHost.dispatch → 5454 agent 默认拒绝 │
└───────────────────────────────────────────────────────────────┘
                 ▼
┌─ src/modules/（28 → 30）──────────────────────────────────────┐
│  新增 dashboard 模块：5 条只读路由 + 1 条低风险写路由               │
│  新增 search   模块：1 条只读聚合路由                             │
│  复用（不新建）：GET /api/status、/api/dsh/model、                │
│                  /api/tokens/summary|series|recent、             │
│                  /api/pending、/api/socialV2/state|prompt、       │
│                  /api/slhag/*、/api/roles/*、/api/_modules        │
└───────────────────────────────────────────────────────────────┘
```

**为什么是这个落点**：
- 集中闸门在 `src/bridge.js:5295-5423`，**在模块委派之前**。新模块的路由不需要自己写鉴权就已被 12 道闸门保护；`src/bridge.js:5454` 的 agent 默认拒绝白名单又会自动挡住 agent token。**所以新模块的第一行鉴权只需 `rejectConsoleOnly`，作为「闸门表改了以后」的兜底**（现有 `core/config.js` 头注释就是这么解释的）。
- 前端已有一个 `api(path, method, body)` 封装（`public/console.html:2630`），读 `localStorage.consoleToken` 放 `x-console-token`。新页面**复用它的头**、但自己判 `res.ok`（R10）。

>   appStartedAt: Date.now(),

### 4.5 回退设计（每步独立可回退）

**关键决定：新模块自带开关，不依赖 `modules.enabled` 一刀切。**

在 `src/modules/index.js` 的 `defineModules(_ctx)` 里新增两行时，**不直接 push**，而是：

```js
// 面板两件套：单独开关，坏了只关它们俩，不影响其余 28 个模块。
const panelOn = _ctx.cfg?.socialV2?.modules?.enabled !== false;
if (panelOn && _ctx.cfg?.socialV2?.modules?.dashboard !== false) list.push(dashboardModule);
if (panelOn && _ctx.cfg?.socialV2?.modules?.search !== false) list.push(searchModule);
```

- 开关位置：`cfg.socialV2.modules.dashboard` / `cfg.socialV2.modules.search`（**已有的 `modules` 子对象里**，因此 `loadConfig` 白名单不用动，见 R13）。
- 关闭方式：控制台把 `modules.dashboard` 设成 `false`（或直接改 `config.json`）→ 重启 bridge → 模块不装载 → 对应路由 404 → 前端 section 自动隐藏（前端按 `/api/_modules` 的 `by_module` 判断）。
- **最坏情况**（新模块让 bridge 起不来）：`modules` 子对象整个被跳过，模块化重启，老路由接管；再不行就 `git checkout` 那 4 个改动文件（都是新增文件 + 2 处单行改动，回滚成本极低）。

**前端回退**：`section-dashboard` 用 `data-page="overview"` 且默认 `hidden`，由 JS 在 `/api/_modules` 返回 `by_module.dashboard` 存在时才移除 `hidden`。**后端关掉 = 页面自然消失**，不需要再动 HTML。

## 6. 明确不做的事

| 不做 | 理由 |
|---|---|
| **不新建独立常驻服务 / 独立端口** | 方案在这里是对的。available 559 MB、nproc 2（F9），3100 已由 systemd `Restart=always` 守护，复用零成本 |
| **不引入任何前端框架或图表库** | 现状零 devDependencies、7 个纯 JS 运行依赖（F28）；`test:console-ui` 的基线机制建立在单文件 `console.html` 上（R9） |
| **不重写路由体系 / 不改 `registry.js` / 不动 `modules.enabled` 开关** | 这是阶段 27 事故的复盘红线（F26/F27）；新增只用标准 `register` 契约 |
| **不自己实现 socialV2 配置写入** | `normalizeSocialV2` + `{...current, ...body}` 白名单合并是防「静默打开默认关闭工具」的关键（F17），另写一份必然分叉（R12） |
| **不新增顶层配置段** | `loadConfig` 白名单会静默丢弃（F19）；开关塞进已有的 `cfg.socialV2.modules` 就绕开了 |
| **不做备份 / 恢复页面** | `state/` 82 MB，恢复语义未验证；做错会把 28 个模块的 state 混着重放（R8）。首版只给「配置导出成文本」 |
| **不做日志导出、不做任意时间范围查询** | 活动流是 `createCappedLogger(…, 500)`，只留 500 行（R6），做时间筛选等于假装有数据 |
| **不做磁盘用量（`df`）** | 需要子进程；收益低（磁盘很少成为问题），风险高（新增命令执行面） |
| **不做 provider 切换、不做 DSH 插件安装** | 属 provider-switch / DSH 各自领地（F15），面板只读现状 |
| **不做内存 / 情绪 / 日记 / 画像 / 日程的第二个读写入口** | 已有 `memory`(5) / `ai-extras`(6) / `share`(4) / `social`(4) 等路由（F23），重复实现必然两套状态机打架 |
| **不做第二套花费看板** | `section-usage` 已经完整（四指标 + 四种窗口走势 + 按会话 + 逐轮明细）（F24） |
| **不做 multi-user / 权限分级** | 主人一个人用。多用户只会增加鉴权复杂度和绕过风险 |
| **不加「服务启停白名单」** | 现有只有 `POST /api/restart`；加白名单就要加 systemctl 调用 = 新增命令执行面。重启一个动作够了 |
| **不改前端 `api()` 的错误处理** | 它被 18 个 section 共用，改了会连锁影响；新页面自己判 `res.ok`（R10） |
| **不做「未接入」占位开关** | 方案自己写了「不以可点击开关伪装已生效」——照做：后端没有的就**不渲染**，而不是渲染成灰按钮 |

## 7. 给下一个实现代理的三条硬提醒

1. **先读 `docs/模块契约.md` 再写第一行代码**。六条规则里最容易踩的是「注入块对象字面量的值位置不能引用注入点之后声明的名字」——`config.js` 里 5 条路由、`inspect`/`memory` 两个注入块的注释都在讲同一件事（`src/bridge.js:4216`、`:4226`）。
2. **每改一处就跑一次 `GET /api/_modules`**。`registry.routes` 的数字变化必须正好等于你这步新增的路由数；`problems` 必须仍然只有那 3 条 `route-shadow`。数字不对就是「整段删除 + 部分搬运」的味道。
3. **任何接口先问「agent 能不能打进来」**。虽然 `src/bridge.js:5454` 的默认拒绝会兜住，但那是一张按路径字面量维护的表；模块内仍然写 `rejectConsoleOnly` 作为第二道（`src/modules/core/config.js` 头注释逐字解释了为什么这不冗余）。

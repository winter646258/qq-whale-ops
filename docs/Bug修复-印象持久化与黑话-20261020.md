## 一、Bug 1：印象维护的两个计时字段从来没被存盘

### 现象

状态文件 `state/social-v2.json` 里 **`lastImpressionRefreshAt` / `lastImpressionNudgeAt` 是 undefined**。

### 根因

这两个字段：
- `loadSocialV2State()` 里**读**（8511 / 8513 行）
- 新建会话时**给默认值**（8431 / 8432 行）
- **`saveSocialV2State()` 的字段清单里没有它们**

于是每次跑起来内存里有、写盘时被丢掉、重启再读回来又是缺的。

### 后果（这才是它值钱的地方）

1. **「7 天提醒她重写印象」永远触发不了** —— 因为 `lastImpressionRefreshAt` 每次重启都变回"现在附近"，`impressionStale` 永远为假。这正是交接文档待办 #7「印象只增不减」的**真正根因**。
2. **「记印象」驱动的 12 小时冷却永远失效** —— `lastImpressionNudgeAt` 丢失 ⇒ 每次重启视为"从没念过"。

### 修法（三层）

**a) save 里补两行**

```js
lastImpressionRefreshAt: Number(st.lastImpressionRefreshAt) || 0,
lastImpressionNudgeAt: Number(st.lastImpressionNudgeAt) || 0,
```

**b) 顺便修一个语义陷阱**：load 缺失时旧逻辑给 `Date.now()`（= "刚刷新过"）。

这看起来是"防唠叨"，实际上把**「从未刷新过」和「刚刷新过」变成了不可区分**，
于是 7 天提醒**永远**不会来。改成给 `0`（明确表示从未刷新）。

> 防唠叨本来该由 `lastImpressionNudgeAt` 的冷却负责，不该靠伪造刷新时间来兜。

**c) 新建会话初始化也改成 0**，与 load 保持一致。

### 附带修的 Bug 1-d：`interactionCount` 从不自增

实测 6 条印象的 `interactionCount` **全是 1**。全代码里只有两处写它：
- `appendMemoryV2` 新建时给 1
- `memory-update` 端点手动传值时改

所以「互动次数」永远停在第一次记印象的那一刻。而它正是判断「这条印象该不该重写」的依据之一。

修法：在**消息入库**和**拍一拍事件**两处，给**已有印象的人** +1：

```js
const im = st.memberImpressions && st.memberImpressions[sender];
if (im && typeof im === 'object') {
  im.interactionCount = (Number(im.interactionCount) || 0) + 1;
  im.lastSeenAt = Date.now();
}
```

**关键约束：只给已有印象的人加，不新建印象。**
凭空给每个发言的人都记一条，那是"用户画像"，不是"她的印象"——这条边界必须守住。

## 二、Bug 2：黑话研究断点

### 先纠正一个误判

早上咱说"黑话坏了、240 条一条没进提示词"。**更准确的说法是**：

黑话系统**按设计就是人工审核制**：
1. 提取出候选（`status: candidate`）
2. 达到研究阈值（默认 `[2,4,8]`）⇒ AI 去查释义
3. 人工在控制台 `/api/slang/batch-confirm` 点确认 ⇒ `status: confirmed`
4. 只有 `confirmed` 且有 `meaning` 的才进 `buildSlangContext`（提示词）

240 条全是 candidate，说明**第 3 步从没发生过**（没人去点确认）。这不是代码坏了。

### 真断点 a：达到阈值却从没研究的词

实测 `魔了` / `lt` 两条 `count=2`（已达阈值）但 `lastInferenceCount=0`（从没研究过）。

根因：入队只在该条**再次出现**时触发。一条达到阈值后不再出现的词会永久卡住。
研究失败（21:07 / 21:12 的「学习会话 turn 未正常完成」）后也一样卡住。

**修法**：抽一个独立函数 `sweepUnresearchedSlang()`，由两处调用：
- 每次提取后
- **服务启动后延迟 30 秒**

> ⚠️ 第一版补丁把它写在「提取成功」分支里 —— 实测**没触发**：21:37 那次是「未发现候选」，
> 之后没有新提取，补偿永远等不到机会。所以才改成独立函数 + 启动时调用。

**实测证据**：
```
21:49:59 [bridge] 黑话研究：补偿扫描补入 2 条从未研究的候选（启动补偿）
21:50:16 [bridge] 黑话研究：魔了 未确认，保留候选待后续研究
21:50:16 [bridge] 黑话研究：lt 未确认，保留候选待后续研究
```

### 真断点 b：`batch-confirm` 的拒绝理由太含糊

原逻辑：`if (!entry.meaning) { skipped.push({ reason: '缺少含义' }); continue; }`

问题在于**为什么不能确认**没讲清楚：确认了也不会进黑话表（`buildSlangContext` 会过滤掉），
等于白确认。改成：

```js
reason: '缺少含义：请先等 AI 研究出释义（或手动补 meaning）再确认，否则确认了也不会进黑话表'
```
并回传 `count`，便于判断是不是热门词。

### 一个重要的**不修**

「魔了 / lt 研究后仍 `meaning` 为空」**不是 bug，是防幻觉设计在起作用**。

看它们的证据：
```
魔了 | 证据: ["魔了", "魔了"]
lt   | 证据: ["lt", "@INFINITY_KARAKURI❤️ lt分低一点"]
```

只有孤立的两个字/两个字母，**没有任何语境**。研究 prompt 要求 `confirmed: true` 才写回，
AI 判定"不确认"是**正确行为** —— 它没有瞎编一个释义。

而 `lt` 那条明显是 `@某人 lt分低一点` 里的碎片，连是不是黑话都不确定。

> 把"研究过但没确认"当成"卡住"是错的。**宁可留空，不要编造** ——
> 编出来的释义会直接进她的提示词，污染她对这个词的理解。

## 四、踩过的两个坑（记下来省得再踩）

1. **同一段代码在两处出现**：`st.recentMessages.push(msg)` 那段锚点在
   `appendSocialV2Message` 和 `appendSocialV2Poke` 里各有一份（完全相同）。
   第一版补丁用 `count != 1` 检查直接报错。
   ⇒ **拍一拍也算互动**，两处都该打，改成 `count == 2` 并替换全部。

2. **补偿扫描挂在错误的位置**：写在「提取成功」分支里，实测因「未发现候选」永不触发。
   ⇒ 这类"补偿/兜底"逻辑**不能依赖主流程刚好走到**，必须有独立的触发点（启动时）。

## 五、遗留：黑话仍然需要人点确认

修完之后系统能力齐了，但**第 3 步（人工确认）仍然没人做**。当前状态：

- 总 245 条候选，5 条有释义
- 0 条 confirmed ⇒ 提示词里仍然没有黑话表

**这不是 bug，是流程没走。** 要生效需要：

```bash
# 看有哪些候选有释义（这些才能确认）
curl -s -H "x-console-token: $T" http://127.0.0.1:3100/api/slang | ...

# 批量确认
curl -s -X POST -H "x-console-token: $T" -H 'content-type: application/json' \
  -d '{"ids":["<id1>","<id2>"]}' http://127.0.0.1:3100/api/slang/batch-confirm
```

或者把确认权交给她自己（给她一个 `qq_slang_confirm` 工具）——
但那等于让她自己决定"这词我懂了"，需要单独讨论是否合适。

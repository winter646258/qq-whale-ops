## 一、先说结论：能抄什么，不能抄什么

`tv.md` 那套是在**另一台机器**上给**六个 AI 室友共用同一个「AI 小屋」账号**做的，和你这边「小鲸鱼一个人格」的模型不一样。照搬会带来一堆用不上的复杂度。

| tv.md 的部件 | 你这边要不要 | 理由 |
|---|---|---|
| `world.py` 世界调度器（谁刷、何时刷、一起刷还是单人刷） | **不要**，换成轻量版 | 那是六人合租的排班需求。一个人格只需要「什么时候想刷」 |
| `browse.py` 执行器主流程（领任务→拉候选→选内容→生成感想→写动作） | **要，这是核心** | 真正值钱的是这个「看→想→做」的三段式 |
| `bili.py` / `heybox.py` 站点客户端 | **要**，但可以瘦身 | WBI 签名、hkey 签名这些签名逻辑必须抄，否则接口调不通 |
| `phone.py` + Chrome 扩展（浏览器代理，Cookie 留在浏览器） | **要**，这是安全底线 | 直连带 Cookie 的 API 等于把账号密码写进服务器 |
| `screen.py` MuMu 模拟器 + ADB 电视互动 | **不要** | 你要的是她自己刷，不是六个人挤在客厅指挥点击 |
| `snapshot` 视觉模型描述每轮画面 | **不要** | 同上 |
| `browse.db` 账本 + `browse_report` 回流世界 | **要，但改形状** | 不必做完整世界系统，但「她确实看过这个视频」这个事实必须落盘，否则她是在编造经历 |
| 合租号署名 `——角色名` | **不要** | 只有一个账号，签名反而暴露 |

**一句话**：抄「执行器 + 签名客户端 + 浏览器代理 + 账本」，砍掉「多角色排班、电视互动、合租号」。

## 二、为什么必须走浏览器代理，不能直连

这是整个方案里**唯一不能妥协**的一点。

B 站和小黑盒的写操作（点赞、评论、收藏）都需要登录态。有两种做法：

- ❌ **把 Cookie 存到服务器上直接请求**：Cookie 是长期凭据，一旦服务器日志、备份、`git` 历史里漏出去，账号就没了。而且 B 站 cookie 有几个字段（`bili_jct` 是 csrf、`SESSDATA` 是会话）混在一起，泄露 `SESSDATA` 就能直接冒充。
- ✅ **Cookie 留在你自己的浏览器里，服务器只发「请求指令」**：服务器把「要请求什么 URL、什么方法、什么参数」放进队列，浏览器扩展在自己的标签页里带着已有登录态发出去，再把响应体回传。服务器**从头到尾看不到 Cookie**。

`tv.md` 第 5 节描述的正是这个模型，值得照抄。代价是要写一个小 Chrome 扩展（约 150 行），而且**你的浏览器必须开着**。

### 一个必须提前想清楚的问题

浏览器代理模式下，**服务器能不能刷站取决于你的电脑开没开**。

`tv.md` 第 12 节第 2 条专门警告过这个坑：`phone_mode="cloud"` 只是「排班认为手机可用」，真正能不能执行还要看 `Bridge.online()`。

对你这边的含义：

- 你电脑关了 → 刷不了 → **任务应该记为「没刷」而不是「刷了但没看到」**
- 绝不能在离线时让她以为「我刷过了」然后编造内容

这一条要写进执行器的硬约束。

## 三、整体架构（落到你的机器上）

```
┌─────────────────────────────────────────────────────────────┐
│  /opt/qq-bridge                                              │
│                                                              │
│  bridge.js                                                   │
│    ├─ 唤醒 prompt 里加一行「你想去 B 站看看吗」               │
│    ├─ MCP 工具 qq_browse（她主动请求刷站 / 看某个链接）        │
│    └─ 睡眠整合时把「今天刷到了什么」带进回顾                   │
│                                                              │
│  src/browse-runner.js        ← 新，执行器                     │
│    ├─ 拉候选（推荐/关注/分区）                                 │
│    ├─ 模型选内容（复用现有 DSH 调用，不加新模型）              │
│    ├─ 生成感想与互动意愿                                      │
│    ├─ 过安全闸门（长度/敏感词/频率/去重）                     │
│    └─ 提交动作                                                │
│                                                              │
│  src/site-bili.js            ← 新，B 站客户端（WBI 签名）      │
│  src/site-heybox.js          ← 新，小黑盒客户端（hkey 签名）   │
│                                                              │
│  src/browse-ledger.js        ← 新，账本（JSONL，与现有 state 同风格）│
│                                                              │
│  state/browse/                                               │
│    ├─ seen.jsonl    看过什么（去重）                          │
│    ├─ actions.jsonl 做了什么（点赞/评论/收藏，含成败）         │
│    ├─ sessions.jsonl 每轮会话记录（模型调了几次、读了几个）     │
│    └─ settings.json 开关、配额、时段                          │
└─────────────────────────────────────────────────────────────┘
                            │ HTTP 长轮询
                            ▼
         ┌──────────────────────────────────┐
         │ 浏览器扩展（在你 Windows 上跑）    │
         │   GET  /phone/poll   领任务       │
         │   POST /phone/result 回传响应     │
         └──────────────────────────────────┘
                            │ 带已有登录态
                            ▼
              bilibili.com / api.xiaoheihe.cn
```

**关键取舍**：`browse-runner.js` 不新开进程，作为 `bridge.js` 的一个模块跑在现有进程里。理由：你机器只有 **1736MB 内存，当前 available 663MB**，再开一个 Node 进程带模型 SDK 不划算。现有 `qq-bridge` 进程已经 101MB，加这个模块估计 +30~50MB。

## 四、分几期做

### 第一期：只读（1~2 天）

**目标**：她能看见 B 站推荐和某个视频的标题/简介/标签/热评，能说「今天看到个有意思的」，但**不能做任何写操作**。

要做的：

1. `src/site-bili.js` —— 只要三个只读接口：
   - `/x/web-interface/wbi/index/top/feed/rcmd`（推荐流）
   - `/x/web-interface/view`（视频详情）
   - `/x/v2/reply`（评论）
   - 需要 WBI 签名（`img_key`/`sub_key` 从 `/x/web-interface/nav` 拿，然后 `mixinKeyEncTab` 置换 + 两次 md5）
2. `src/phone-bridge.js` —— 服务器侧队列 + 长轮询端点（`/phone/poll`、`/phone/result`），60 秒心跳判定在线，单任务 30 秒超时
3. Chrome 扩展 —— 只实现「收到 URL 就在指定域名的标签页里 fetch，回传响应」
4. `state/browse/settings.json` 里**只开读数，写操作全关**

**验收标准**：能稳定列出 20 条推荐标题 + 打开一条视频读到简介和热评；任何写请求在代码层面就是不可达的（不是配置关掉，是没实现）。

> 为什么第一期不做写操作：写操作一旦出问题（点赞错人、评论发到不该发的地方），是**不可撤回**的。先把「读」跑稳，让她对内容的理解质量看得见，再决定要不要给手。

### 第二期：写操作（2~3 天）

**目标**：能点赞、收藏、关注；评论需要额外一道人工/模型复核。

要做的：

1. `src/site-bili.js` 加写接口（`/x/web-interface/archive/like`、`/x/v3/fav/resource/deal`、`/x/relation/modify`）
   - 都需要 `bili_jct`（csrf）—— **这个值必须由扩展在浏览器上下文里注入**，服务器只放占位符 `__BILI_JCT__`
2. `src/browse-safety.js` —— 安全闸门，这一层比什么都重要：
   - **频率**：每分钟最多 2 次写操作，每小时最多 15 次
   - **去重**：`seen.jsonl` 里做过的就不再提
   - **同一 UP 主每日评论上限**：1 条（防盯着一个人刷）
   - **两次评论最小间隔**：30 分钟
   - **敏感词 / 长数字 / 链接**：直接拒（防止被诱导发广告或泄露信息）
   - **二次审核**：公开发言（评论、动态）生成后**再过一遍模型**，问它「这句话像不像 AI 在硬蹭」，不过就不发
3. `state/browse/actions.jsonl` 记账 —— 每条记录 `{ts, site, itemId, action, content, ok, error}`

**验收标准**：能对一个视频点赞 + 收藏 + 发一条评论；把敏感词塞进去会被拦；连续快速点赞会被限流；同一条内容不会重复点赞。

### 第三期：自主节奏（1 天）

**目标**：不是「你叫她刷她才刷」，而是她自己有「今天想看看什么」的念头。

要做的：

1. 在唤醒 prompt 里加一行**低权重**的提示（不是每次都出现，按概率 15%）：
   ```
   【可以做的事】如果现在想放松一下，可以用 qq_browse 去 B 站/小黑盒看看。
   不想去就不去，不用勉强，也不用报告"我没去"。
   ```
2. `state/browse/settings.json` 里配时段：默认只在 **20:00~23:00** 给这个机会（她自己 22 点最活跃，日志里 22 时 124 条消息）
3. 每日次数上限：默认 **2 次**，每次最多看 **5 个内容**
4. **回流**：刷完之后，账本里的记录要能被两处读到：
   - 睡眠整合（凌晨 4 点回顾）读「今天看了什么」
   - 群聊近况（D 功能）读「她最近在关注什么」

**验收标准**：她会在晚上自己提起「刚看了个视频」；你说「你在 B 站看到什么了」她能答上来，且内容对得上账本。

### 第四期（可选，再说）：小黑盒

小黑盒的签名（`hkey`/`nonce`/`_time`）比 B 站更绕，而且它的接口变动更频繁（`tv.md` 第 4.3 节末尾特意写了「接口兼容性仍取决于平台的实际行为」）。

**建议**：B 站跑稳三个月后再上小黑盒。小黑盒的价值主要在游戏资讯，而你这边群里聊的似乎不是这个重心。

## 五、和现有系统的接点

这部分是**最容易出问题**的地方 —— 新模块和已有功能抢资源。

| 现有功能 | 接点 | 风险 |
|---|---|---|
| 唤醒 prompt 拼装 | `buildWakePromptV2` 加 `browseLine` | 锚点又在 `const base = roleLine + tokenLine + ...` 那一行，**插错过一次（`sharedMemoryLine` 算了没进 prompt）**，这次必须断言锚点唯一 |
| 睡眠整合 | `formatSleepReviewMaterial` 加「今天刷到」 | 素材不能太长，现在 `REVIEW_MAX_CHARS=1200` 已经快满了 |
| 群聊近况（D） | `formatGroupDigestLine` 不用改，但「她关注什么」可以作为候选 | 别做成「她一刷站就汇报给主人」，会变刷屏 |
| 记忆系统 | 值得记的内容用 `qq_shared_memory` 存 | 注意 scope：B 站看到的东西**默认不共享给群**，`owner_private` 起步 |
| 心情系统 | 刷到喜欢的内容可以影响 PAD | 可选，别做成「点赞=开心」这么机械 |
| 好感度 | 不接 | 无关 |
| DSH 事件流 | 不需要 | 刷站是后台任务，不走 DSH 回合 |

## 六、你机器上的硬约束（必须先解决）

### 1. 内存

```
total 1736MB / used 899MB / available 663MB / swap 已用 777MB
```

大进程：`dsh` 279MB、`bridge` 101MB、`node runtime` 96MB、`mcp-snowluma-safe` 69MB、`mcp-web-search-safe` 61MB。

`browse-runner` 要调模型选内容 —— **如果复用 DSH 的会话，不额外占内存**；如果另起一个模型进程，至少 +150MB，触发 OOM 的风险不小（`qq-dsh.service` 有 `OOMScoreAdjust=200`，是被优先杀的那个）。

**建议**：先用**现有 DSH 会话**做内容理解（发一个内部 prompt 让它挑），不另起进程。

### 2. 浏览器必须开着

这是浏览器代理模式的固有代价。要接受「你电脑关机 = 她刷不了站」。

**如果不接受**，唯一替代方案是把 Cookie 存服务器 —— 我强烈不建议，理由见第二节。

### 3. 时区与活跃时段

她北京时间 22 点最活跃（124 条/小时），23 点骤降到 5 条。刷站时段定在 20:00~23:00 是合理的。

## 七、安全边界（写死在代码里，不做成配置开关）

这些不做成「可以在控制台关掉」的配置，而是写进代码的硬判断：

| 边界 | 判断 |
|---|---|
| 只读 vs 写 | 第一期代码里根本没有写函数，不是开关 |
| Cookie | 服务器侧永不持久化；`phone.py` 只转发 URL/方法/头/体，不收 Cookie 字段 |
| csrf 占位符 | `__BILI_JCT__` 只在扩展侧替换，服务器日志里出现真实值要报错 |
| 公开发言 | 评论/动态**必须**过二次模型审核，且审核 prompt 要问「像不像 AI 硬蹭」而非「有没有违规」 |
| 私密信息 | 评论内容里出现 `ownerQQ`、`consoleToken`、`agentToken`、`SENSITIVE_RE` 命中词 → 直接拒 |
| 频率 | 见第三期第二部分的数字，硬编码 |
| 风控 | 遇到 `-412`（B 站风控）/ `403` → 该站点暂停 3 小时；连续 3 次 → 需要人工在控制台恢复 |
| 撤回 | **不做**。点赞可以取消，但评论删不掉 —— 所以评论这道闸门要最严 |

## 九、我的判断：值不值得做

**值得，但别按 tv.md 那种规模做。**

决定要不要做的关键问题不是「技术上能不能」，而是：

**她现在（不刷站）说的话，有没有「没有生活」的感觉？**

- 如果她在群里只能接话、说不了「我昨天看了个视频」这种有具体内容的事，那刷站确实是块短板 —— 值得做
- 如果她靠现有的群聊、私聊、记忆已经够充实，那刷站只是**增加一个信息源**，不是补短板 —— 优先级可以往后放

从最近的日志看，她其实已经会说「早上 dsFY 跟另一只小鲸鱼在约定『第二锅出来喊你』」这种具体的观察，说明**群聊本身已经提供了足够的「生活素材」**。

所以我的建议是：**先做第一期（只读）验证质量**。如果她看了视频说出来的感想确实有意思、确实像她想说的，再往下做；如果只是复述标题，那这套东西加进来只是噪音。

## 十、如果决定做，第一步是什么

不是写代码，是**先跑通一次手动的浏览器桥**：

1. 写一个 30 行的 Chrome 扩展（只支持「收到 URL → fetch → 回传」）
2. 在 `bridge.js` 里加两个只有本机能访问的端点：`/phone/poll`、`/phone/result`
3. 手动从服务器发一条「取 B 站推荐」的请求
4. 看能不能拿回 JSON

**这一步跑通了，整个方案才成立。跑不通，后面都是纸上谈兵。**

而且这一步的代价很小 —— 扩展可以一直用，之后不管做什么浏览器自动化都能复用。

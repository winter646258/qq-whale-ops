## 一、为什么改（线上证据）

### 5a 别人互拍也会叫醒她

`handlePokeNotice`（改动前 `bridge.js:11111`）算出了 `targetIsSelf`（`bridge.js:11145`），
但**从来没被用到**。`bridge.js:11165` 只判了开关：

```js
} else if (st.wakeConfig?.triggers?.poke) {
  scheduleWakeV2(key, 'poke');
}
```

后果：群里 A 拍 B，她也当自己被拍醒来。群聊每小时唤醒额度只有 8 次，
被互拍吃光之后真正 `@` 她的消息只能打一行「唤醒频率超限，跳过」
（10-21 08:06:21 `keyword:大肥鱼`、08:07:52 `probability` 就是这么被丢的）。

唤醒文案当时写的是「可能拍了你，也可能拍了别人」——文案诚实地承认了逻辑本身没判断。

### 5b 主人 @ 被「会话繁忙」吞掉，而且重启就丢

`/var/log/qqbridge.log` 实测（08:00 之后）：

| 事件 | 条数 |
|---|---|
| 会话繁忙，暂存唤醒原因 | 5（**全是 private**：08:54:07 / 08:55:02 / 08:57:37 / 09:01:20 / 09:01:27）|
| 补发繁忙期间积压的唤醒 | 0 |
| 已被当前回合处理，跳过补发 | 1 |

三个独立原因叠在一起：

1. **FIFO**：入队 `push`、出队 `shift`。一条低优先级 `probability`（20 分）排在队首，
   后面进来的 `@`（90 分）/ 私聊（100 分）只能排在它后面。
2. **只有一个出队时机**：turn 正常结束时 `shift` 一条。重启、会话被替换、
   回合异常，都不会走到那里。
3. **队列只存内存**：`pendingWakeReasons` 不在 `saveSocialV2State()` 的显式字段白名单里
   （`bridge.js:8739`）。桥接 08:52:34 和 09:01:54 各重启一次，队列直接清零 ——
   所以 5 条暂存一条都没补发。

### 6 主动档期每次重启都被重抽

`scheduleProactiveCheckV2()`（`bridge.js:10604`）每次都现抽随机：

```js
const delay = Math.floor(min + Math.random() * (max - min));
```

档期不落盘 ⇒ 重启就重新抽。同一个 `group:910502749`，08:52 重启后是 78min、
09:01 重启后是 96min —— 已经等过的 40 分钟白等了。

## 二、改了什么

### 5a poke 目标判定

```js
// 私聊没有 target_id 时按拍摄她处理：私聊里的拍一拍天然指向对方。
const pokedMe = targetIsSelf || (kind === 'private' && !targetId);
...
} else if (!pokedMe) {
  log(`[reserved2] 拍一拍目标不是她（${senderId} -> ${targetId}），只记录不唤醒 ${key}`);
} else if (st.wakeConfig?.triggers?.poke) {
  scheduleWakeV2(key, 'poke');
}
```

拍别人时：**事件照样进消息流**（她看得到、可以接梗），但**不唤醒、不烧额度**。
唤醒文案同步改成「有人拍了一拍你」。

保守取舍：群里 `target_id` 缺失时判为「不是拍她」。宁可不唤醒，也不去烧额度。

### 5b 优先级队列（纯函数，可单测）

| 函数 | 作用 |
|---|---|
| `enqueuePendingWake(st, reason, seq)` | 按 `wakePriorityV2(reason)` 入队；满 20 条时**丢优先级最低**那条（同优先级丢最早入队的），而不是丢最早的 |
| `pickPendingWakeIndex(st)` | 取最高优先级；同优先级先入先出 |
| `drainPendingWakeFor(key)` | 出队补发；仍忙就放回；已过期（`PENDING_WAKE_TTL_MS = 30min`）或已被本回合处理（`unread` 里没有该 seq）则跳过 |
| `sweepPendingWakeReasons()` | 每 30s 巡检兜底：忙的跳过，不忙的直接补发 |

出队时机从「turn 结束时 `shift` 一条」换成 `drainPendingWakeFor(key)`，
并加了兜底巡检 —— 重启 / 会话被替换 / 回合异常也能补上。

队列进 `saveSocialV2State()` 白名单、进 `loadSocialV2State()`、进新会话默认字段。

### 6 主动档期持久化

```js
const storedNextAt = Number(st.proactiveNextAt) || 0;
if (storedNextAt > nowMs + 1000) {
  delay = Math.min(storedNextAt - nowMs, max * 2);  // 续档，最多续 max 的两倍
} else {
  delay = Math.floor(min + Math.random() * (max - min));  // 过期才重抽
}
st.proactiveNextAt = nowMs + delay;
if (!opts.skipSave) saveSocialV2State();
```

`clearSocialV2Timers()` 同时把 `proactiveNextAt` 清零，
避免下次启动按一个已经作废的旧档期续期。

## 三、过程中撞出来的两个坑（都会要命）

### 坑 1：`const` 的 TDZ —— 差点让整份 socialV2 状态读不出来

第一版在 `saveSocialV2State()` 里用了 `slice(-PENDING_WAKE_MAX)`。看起来没问题，
但 `loadSocialV2State()` 在模块初始化时就会调用 `saveSocialV2State()`，
那时 `const PENDING_WAKE_MAX` 还没初始化 ⇒ `ReferenceError: Cannot access 'PENDING_WAKE_MAX' before initialization`。

隔离副本实测直接报：

```
读取 socialV2 状态失败: Cannot access 'WAKE_PRIORITY' before initialization
```

同一个坑还有第二处，更隐蔽：`load` 里给队列条目补优先级时调了
`wakePriorityV2(r.reason)`，而它读的 `const WAKE_PRIORITY` 表声明在 `main()` 里
**更靠后**的位置。生产上这一版**只要重启就丢光全部会话状态**。

修法：
- `save`/`load` 里用字面量 `20`，不用那个 const；
- `load` 里**不查表**，`pr` 缺省存 0，优先级在**用时**才算
  （`Number(x.pr) || wakePriorityV2(x.reason)`，优先级恒 > 0，所以 0 是安全哨兵）。

教训：`const` 在同一函数作用域里是「按文本顺序初始化」的。
`main()` 这种巨型函数里，靠后的 const 在前面的初始化路径里就是不可用。

### 坑 2：隔离副本里 `currentMode` 是 `chat`

`scheduleProactiveCheckV2` 一开始就 `if (currentMode !== 'reserved2') return;`，
而副本没有 `state/mode.json`，默认 `chat`，测试全被判「没排档」。
给测试钩子加了 `setMode/getMode` 才测得动。

顺带摸清：`proactiveAllowed()` 读的是 **`cfg.allow.private` / `cfg.allow.groups`**
（顶层），不是 `cfg.socialV2.allow`；而且主动侧**永远要求显式白名单**
（`friendOnly` 放宽的是接收，不是主动打扰）。
